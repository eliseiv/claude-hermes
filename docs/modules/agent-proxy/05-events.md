# Agent Proxy — Events (SSE)

Ретранслируемые события Hermes API-сервера (`GET /v1/runs/{id}/events`, бери как есть). Контракт событий — внешний (Hermes); прокси проксирует as-is, кроме биллинг-обработки `run.completed`.

| Событие | Полезная нагрузка | Обработка прокси |
|---|---|---|
| `run.queued` | `{run_id, status}` | ретрансляция |
| `run.running` | `{run_id}` | ретрансляция |
| `message.delta` ✱ | `{event:"message.delta", run_id, delta:"<фрагмент текста>"}` — **`delta` несёт ЗНАЧЕНИЕ-СТРОКУ** | ретрансляция |
| `tool.started` | `{event, run_id, timestamp, tool:"<имя>", preview:"<аргумент>"}` — **подтверждено капчей** | ретрансляция |
| `tool.completed` | `{event, run_id, timestamp, tool:"<имя>", duration:<float>, error:<bool>}` — **подтверждено капчей**; поля `result` **НЕТ** | ретрансляция |
| `approval.request` | запрос подтверждения опасного действия | ретрансляция; клиент отвечает `POST /v1/agent/runs/{runId}/approval` |
| `usage.delta` ⓘ | `{step_index, input_tokens, output_tokens, cumulative_input_tokens, cumulative_output_tokens, cumulative_total_tokens, model}` | ретрансляция + **incremental-биллинг** ([ADR-064](../../adr/ADR-064-incremental-agent-run-billing-and-pause-resume.md), под флагом `agent_incremental_billing_enabled`); при OFF — только ретрансляция |
| `run.completed` | `{event, run_id, timestamp, output:"<финальный текст>", usage:{input_tokens, output_tokens, total_tokens}}` — **подтверждено капчей**: носитель — **вложенный `usage`**, имена **БЕЗ** префикса `cumulative_` | **биллинг:** постфактум `consume(idempotency_key=runId)` ([ADR-047](../../adr/ADR-047-usage-based-billing-for-agent.md)) ИЛИ финализация остатка при incremental ([ADR-064 §2](../../adr/ADR-064-incremental-agent-run-billing-and-pause-resume.md)) + ретрансляция |
| `reasoning.available` ⚠ | `{event, run_id, timestamp, text:"<текст>"}` — **не было в docs, обнаружено капчей** | ретрансляция; **в снапшот НЕ накапливается** |
| `run.failed` | `{error, ...}` | ретрансляция; **без debit** (нет usage) |
| `run.truncated` ⚙ | `{event:"run.truncated", run_id, from_seq, reason:"buffer_trimmed"}` | **синтетическое, генерирует control plane** ([ADR-067 §3.4](../../adr/ADR-067-agent-run-background-consumer.md)): реплей начинается не с начала прогона (ring обрезан). Клиент: полученный поток **не полон**, накопленный текст брать из `GET …/state.resultText`. НЕ терминальное |
| `run.paused` ⚙ | `{event:"run.paused", run_id, reason:"credits_exhausted", status:"paused", output:"<промежуточный текст, ≤ AGENT_STATE_RESULT_TEXT_MAX_CHARS, head-preserving>", steps, billed:<charged>, balance:0, usage:{cumulative_input_tokens, cumulative_output_tokens}}` | **синтетическое, генерирует control plane** ([ADR-064 §3](../../adr/ADR-064-incremental-agent-run-billing-and-pause-resume.md)); терминальное для клиента (стрим закроется БЕЗ `run.completed`) |

✱ `message.delta` — **фактическая форма патченого образа ([ADR-065](../../adr/ADR-065-patched-hermes-image-ghcr.md)).** Подтверждена **прод-капчей реального стрима** (первоисточник — сам образ; сохранена как `tests/fixtures/hermes_prod_run_adr065.sse`, прогон `run_d931839587a64e3885b4d096cf7440d0`, 2026-07-29). Текст фрагмента лежит в поле **`delta`** и является **строкой**:

```
data: {"event":"message.delta","run_id":"run_d931839587a64e3885b4d096cf7440d0","timestamp":1785275267.1823528,"delta":"фрагмент ответа"}
```

**Гранулярность — пословная/потокенная** (в капче 15 дельт за 0.58 с, фрагменты вида `"Я"`, `" не"`, `" могу"`), поэтому склейка обязана быть конкатенацией без разделителей.

⚠️ **Чего в этом событии НЕТ (и на что нельзя опираться):** `delta` — **не объект** и **не содержит `.text`**; полей `text`/`content`/`message` на верхнем уровне тоже нет. Извлекатель обязан принимать значение `delta` как строку. **Именно расхождение docs↔образ на этом месте породило прод-дефект:** во всех трёх прогонах замера `agent_run_snapshots.result_text` (а значит и `resultText` в `GET …/state`) оказался **тождественно пуст** — накопитель искал текст не там, куда его кладёт образ. Побочно это сделало неприменимым дискриминатор процедуры замера [Q-066-1](../../99-open-questions.md) (`char_length(resultText)`) — см. [09-testing.md](09-testing.md). Правила накопления/усечения/guard'а ([ADR-066 §6](../../adr/ADR-066-agent-run-state-snapshot.md)) при этом корректны — не работал только извлекатель. Форма — **внешний контракт Hermes**: при bump образа ([TD-036](../../100-known-tech-debt.md)) перепроверять вместе с `usage.delta`. Толерантность извлекателя к обёртке `{text: …}` допустима как defense-in-depth, но **источник истины — `delta`-строка**.

⚠ `reasoning.available` — **событие, которого в docs не было; обнаружено прод-капчей 2026-07-30** (`tests/fixtures/hermes_prod_completed_run_adr067.sse`, `tests/fixtures/hermes_prod_tool_run_adr067.sse`). Несёт `text` с рассуждением модели.

⚠️ **Ловушка: `text` ДУБЛИРУЕТ финальный ответ**, и общий извлекатель `_extract_delta_text` достаёт из него текст **успешно**. Сейчас это безвредно — накопление `result_text` идёт **по имени события** (`message.delta`), а `reasoning.available` в снапшот не пишется. Но если кто-то расширит дельта-обработку «по наличию текстового поля» вместо явного списка имён, **текст ответа удвоится** в `result_text` и в `/state.resultText`. **Инвариант, который нельзя нарушать: события, накапливаемые в `result_text`, перечисляются ЯВНО по имени.**

ⓘ `usage.delta` — **внешний контракт Hermes** (патч образа, per LLM API-вызов loop). **Подтверждено капчей 2026-07-30:** носитель **плоский** (верхний уровень), присутствуют **оба** набора имён — `sources=('top.cumulative','top.per_step')`. `cumulative_*_tokens` — источник тарификации (анти-двойной-счёт). Точки эмиссии (ориентир, проверить при патче): `agent/conversation_loop.py` ~2059, `gateway/platforms/api_server.py` ~4478.
⚙ `run.paused` — **НЕ** событие Hermes: control plane эмитит его при исчерпании баланса (после `stop`→Hermes interrupt), промежуточный результат — из локального relay-буфера. **`output` ограничен `AGENT_STATE_RESULT_TEXT_MAX_CHARS` (64 KB) с сохранением начала** ([ADR-066 §6](../../adr/ADR-066-agent-run-state-snapshot.md)): relay-буфер схлопывается при каждом флаше снапшота, поэтому в момент паузы доступен ровно тот же усечённый head-preserving текст, что и в `agent_run_snapshots.result_text`. Полный текст — только через `/events`.

## Wire-формат и диспетчеризация клиента
- ✅ **`timestamp` (float, epoch-секунды) есть у ВСЕХ типов событий образа** — подтверждено капчами 2026-07-30 ([Q-067-7](../../99-open-questions.md) **Closed**): `message.delta` 819/819, `usage.delta` 5/5, `tool.started` 2/2, `tool.completed` 2/2, `run.completed` 2/2, `reasoning.available` 2/2.
- ⚠️ **Единственное исключение — наше синтетическое `run.paused` (0/1): метки НЕТ.** Потребитель, полагающийся на «`timestamp` есть всегда», сломается именно на нём. Правило: `timestamp` — признак **события образа**; события, которые генерирует control plane (`run.paused`, `run.truncated`), метки не несут. ⚠️ **Синтетические события control plane метки не несут:** `run.paused` (подтверждено капчей) и `run.truncated` (наше, [ADR-067 §3.4](../../adr/ADR-067-agent-run-background-consumer.md)). Практическое значение: `timestamp` — **единственный надёжный дискриминатор живости прогона** при замере семантики буфера ([Q-066-1](../../99-open-questions.md), [09-testing.md](09-testing.md)) — «событие с меткой позже момента обрыва предыдущей подписки» проверяется прямо по телу события, без обращения к `/state`.
- **Каждое событие сопровождается SSE-полем `id: <epoch>-<seq>`** ([ADR-067 §3.1/§3.2/§3.4](../../adr/ADR-067-agent-run-background-consumer.md)) — **непрозрачный самоидентифицирующий** курсор прогона (`epoch` — поколение ring'а, `seq` — номер внутри поколения). При реконнекте стандартная SSE-библиотека шлёт его обратно в `Last-Event-ID`, и broker отдаёт только новые события; при несовпадении поколения (перезапуск Redis / `FLUSHDB` / TTL) курсор трактуется как пустой → полный реплей, предварённый `run.truncated`. Клиенту разбирать значение не нужно. Поле аддитивно: клиент, диспетчеризующий по JSON-полю `event`, его игнорирует.
- Все события — SSE-строки вида `data: {json}` (единый транспорт Hermes, [ADR-045 §3](../../adr/ADR-045-hermes-as-agent-proxy.md)); тип события несёт **JSON-поле `"event"` внутри тела** (напр. `data: {"event":"usage.delta", ...}`, `data: {"event":"run.paused", ...}`), а не SSE-заголовок `event:`. **Клиент диспетчеризует по JSON-полю `"event"`** — включая синтетическое `run.paused` (control plane эмитит его тем же wire-форматом, что и любое Hermes-событие).
- `run.paused` — **терминальное**: после него стрим закрывается **без** `run.completed`. Промежуточный текст ответа — в ключе **`output`** (склеенный буфер `message.delta`; **НЕ `message`**), **ограничен `AGENT_STATE_RESULT_TEXT_MAX_CHARS` (64 KB) с сохранением начала** (relay-буфер схлопывается при каждом флаше снапшота, [ADR-066 §6](../../adr/ADR-066-agent-run-state-snapshot.md)); полный текст — через `/events`. Детализация — в `steps`; `billed` = списанные кредиты, `balance:0`, `usage.cumulative_*` — накопленный расход к точке паузы. Клиент показывает `output`/`steps` и предлагает пополнение → `POST /v1/agent/runs/{runId}/resume`.

## Транспорт потока: keep-alive и признак штатного закрытия (измерено 2026-07-30)

- ⛔ **Периодических SSE keep-alive образ НЕ шлёт.** Проверено на прогонах с длинным tool-call ([Q-067-6](../../99-open-questions.md) **Closed**). Следствие: **молчание в потоке ничем не отличимо от смерти пира на прикладном уровне** — поэтому детектор смерти upstream обязан быть транспортным (TCP keep-alive, [ADR-067 §6.2](../../adr/ADR-067-agent-run-background-consumer.md)), а любые пороги «по молчанию» запрещены.
- ✅ **Единственная comment-строка — `: stream closed`**, одноразовая, в конце **чисто завершившегося** потока.
  **Это наблюдаемый дискриминатор корректного завершения:** `: stream closed` получен ⇒ поток закрыт штатно; не получен ⇒ поток оборвался или завис. Признак дешёвый (виден прямо в потоке, без обращения к БД) и полезен в диагностике и E2E-проверках. ⚠️ **Строить на нём логику биллинга или статуса нельзя** — это транспортный маркер, а не доменное событие: терминальным событием остаются `run.completed`/`run.failed`/`run.paused`.
- **Тайминги (n=3, тёплый инстанс):** `202` → первый байт потока — медиана **0.184 с**, максимум **0.184 с**. Холодный провижининг стоит **6.7 с** на самом `POST /v1/agent/run` (не на потоке). Максимальная пауза **между событиями** на прогоне с инструментами — **3.01 с**.

## Источник событий: broker ([ADR-067](../../adr/ADR-067-agent-run-background-consumer.md))

- **К `GET {base}/v1/runs/{runId}/events` инстанса Hermes подключается ровно один потребитель — наш фоновый consumer.** Обоснование **не зависит от поведения образа** ([ADR-067 §0](../../adr/ADR-067-agent-run-background-consumer.md)): биллинг не может зависеть от присутствия клиента (измерено: 3 прогона → 0 списаний), нужен ровно один владелец биллинга и состояния на прогон, а межпроцессный фан-аут при 4 воркерах gunicorn обязателен в любом случае. ✅ **Подтверждено перемером 2026-07-30** ([Q-066-1](../../99-open-questions.md)): поток **одноразовый** — повторная подписка инертна даже на живом прогоне. Формулировка «два потребителя исключают друг друга», снятая ранее как недоказанная, теперь обоснована замером; при этом решение от неё по-прежнему не зависит (§0).
- **Клиентский `GET /v1/agent/runs/{runId}/events` к Hermes не ходит.** Он читает Redis: `LRANGE agent:run:{runId}:events` (реплей) + `SUBSCRIBE agent:run:{runId}:pub` (live), с дедупом по внутреннему `seq`; правила закрытия стрима — [ADR-067 §3.3](../../adr/ADR-067-agent-run-background-consumer.md) (терминальное событие может не появиться в Redis никогда, и закрывать обязаны мы).
- ⚠️ **Форма событий не меняется, семантика подключения — меняется** ([ADR-067 §3.4](../../adr/ADR-067-agent-run-background-consumer.md)): **каждое соединение `/events` самодостаточно и начинается с реплея с начала прогона**. Клиент, аккумулирующий `message.delta` поверх нескольких соединений, **удвоит текст** — при новом подключении накопленный текст надо сбрасывать. Требует согласования с iOS.
- **Публикация в Redis не троттлится** (троттлинг [ADR-066 §6](../../adr/ADR-066-agent-run-state-snapshot.md) — про запись в Postgres): живой стрим идёт с полной гранулярностью, как и раньше. Запись в ring — **best-effort**: ошибка Redis логируется и не прерывает consumer.
- **Сбой downstream не влияет на upstream:** переполнение очереди медленного подписчика отключает **подписчика**, а не consumer'а (разрыв клиентского SSE безобиден — клиент переподключается и получает реплей; остановка consumer'а стоила бы биллинга).
- **Ring содержит сырые SSE-строки — это user content в Redis** (персистентность RDB, TTL ≤ 1 ч, CASCADE-удаление пользователя его не чистит): [ADR-067 §3.5](../../adr/ADR-067-agent-run-background-consumer.md), [05-security.md](../../05-security.md).
- Kill-switch `AGENT_RUN_CONSUMER_ENABLED=false` возвращает сегодняшнее поведение (прямой relay с биллингом на клиентском пути) — временный двойной путь, [TD-038](../../100-known-tech-debt.md).

## Снапшот-побочные эффекты relay ([ADR-066](../../adr/ADR-066-agent-run-state-snapshot.md))

> ⚠️ **С [ADR-067](../../adr/ADR-067-agent-run-background-consumer.md) исполнитель всей таблицы ниже — фоновый consumer, а не клиентский relay.** Правила (какое событие что пишет, троттлинг, немедленные флаши, условность статусов) — **без изменений**.

Помимо ретрансляции и биллинга, `stream_events` апсертит состояние прогона в **`agent_run_snapshots`** ([03-data-model.md §25](../../03-data-model.md)) и выставляет статусы в `agent_runs` — это единственный источник данных для `GET /v1/agent/runs/{runId}/state` ([02-api-contracts.md](02-api-contracts.md)). Накопление `partial_text`/`steps`/токенов вынесено **из ветки `if incremental:`** — ведётся **всегда**, независимо от `agent_incremental_billing_enabled`. Запись — с явным `commit()` (streaming-context паттерн `_bill_step`, [ADR-064](../../adr/ADR-064-incremental-agent-run-billing-and-pause-resume.md)).

### Инварианты записи
- **Троттлинг** касается только `message.delta`: текст флашится не чаще одного раза в `AGENT_STATE_FLUSH_INTERVAL_SECONDS` (дефолт `3.0`). Терминальные события и `approval.request` флашатся немедленно.
- **Replay-guard (обязателен) — per-column, НЕ row-level.** При переподключении к `/events` Hermes реплеит буфер **с начала**, поэтому новый потребитель стартует с короткого префикса и мог бы затереть более полный текст. ⚠️ **Уточнение 2026-07-29 ([Q-066-1](../../99-open-questions.md)):** посылка «реплеит буфер с начала» — **непроверенное допущение** (H4): прод-процедура её не упражняла. Наблюдение прода иное (вторая последовательная подписка получила 0 байт), но и оно не доказывает дренаж — живость прогона в тот момент не зафиксирована. **Guard корректен при любом исходе** и остаётся обязательным как defense-in-depth (в т.ч. на случай двух consumer'ов при истёкшем lease, [ADR-067 §4](../../adr/ADR-067-agent-run-background-consumer.md)); формулировки SQL ниже менять не нужно. Монотонность применяется **к отдельным колонкам** внутри `ON CONFLICT (run_id) DO UPDATE`:
  - `result_text = CASE WHEN char_length(EXCLUDED.result_text) >= char_length(t.result_text) AND left(EXCLUDED.result_text, char_length(t.result_text)) = t.result_text THEN EXCLUDED.result_text ELSE t.result_text END` — **префиксный** guard: одной длины мало (она ловит укорачивание, но пропустила бы более длинную **подмену** текстом, не продолжающим накопленный). При replay-с-начала ведёт себя как проверка длины; при no-replay ([Q-066-1](../../99-open-questions.md)) снапшот **замерзает** на последнем полном тексте вместо порчи обрывком — клиент видит по `updatedAt` и добирает через `/events`;
  - `input_tokens`/`output_tokens` = `GREATEST(t.…, EXCLUDED.…)`;
  - `pending_approval = CASE WHEN :assert_approval THEN EXCLUDED.pending_approval ELSE t.pending_approval END` — гейт **по семантике источника**, не по длине текста: `assert_pending_approval=true` ставят только апсерты, которые действительно утверждают approval-состояние.

  | Call-site | `immediate` | `assert_approval` |
  |---|---|---|
  | `tool.started` / `tool.completed` | ✅ | **true** |
  | `approval.request` | ✅ | **true** |
  | `run.failed` | ✅ | **true** |
  | `run.completed` | ✅ | **true** |
  | `run.paused` (`_pause_run`) | ✅ | **true** |
  | `message.delta` | ❌ (троттлинг) | **false** |
  | **`usage.delta`** (anchor-флаш) | ✅ | **false** |

  ⚠️ **`immediate` и `assert_approval` — РАЗНЫЕ свойства** (первое про троттлинг, второе про право говорить за approval-состояние). Они совпадают у всех событий, несущих авторитетную approval-информацию, поэтому `assert_approval` по умолчанию наследует `immediate` — но **`usage.delta` требует первого без второго**: якоря токенов обязаны попасть в БД сразу (соответствующий debit коммитится в том же такте, и обрыв SSE сразу после оставил бы ledger списанным, а `/state` — с нулевым usage), тогда как `usage.delta` может законно прийти **после** ответа клиента на `POST …/approval`, и повторное утверждение закешированного approval воскресило бы ложный `waiting_approval`. Иначе периодический флаш текста «воскресил» бы уже снятый через `POST …/approval` approval, и `/state` вернулся бы в `waiting_approval` по работающему прогону;
  - `last_tool`, `updated_at` — **безусловно** `EXCLUDED.*`;
  - row-level **`WHERE t.user_id = EXCLUDED.user_id`** — tenancy-гвард (defense-in-depth под допущение о глобальной уникальности Hermes `run_id`, [Q-066-2](../../99-open-questions.md)): при коллизии `run_id` между пользователями апсерт даёт `rowcount=0` вместо перезаписи чужого снапшота. Чтение симметрично owner-scoped — `snapshots_repo.get(run_id, user_id)`.
  ⚠️ **Row-level `WHERE` как staleness-гейт запрещён** ([ADR-066 §6](../../adr/ADR-066-agent-run-state-snapshot.md)) — гейт по свежести данных (длине/префиксу) блокирует апсерт **строки целиком**, поэтому в replay-окне не записались бы ни `pending_approval` (клиент **никогда** не получил бы `waiting_approval`), ни `last_tool` (замерзает), ни `updated_at` (детект устаревания начинает врать). Поэтому префиксная проверка живёт в `CASE` колонки, а не в `WHERE` строки. Единственный допустимый row-level предикат — **тенантный** (гейт по identity, для легитимной записи владельца истинен всегда → ничего не блокирует). Монотонность нужна только тексту и токенам; `last_tool`/`pending_approval` монотонными **не являются** (инструмент меняется, approval снимается).
- **Head-preserving truncation.** `result_text` **и** `pending_approval.preview` обрезаются **с сохранением начала** одним и тем же `AGENT_STATE_RESULT_TEXT_MAX_CHARS` (дефолт `65536`; обе строки — user content, отдельного лимита под preview нет). Обрезка хвоста запрещена: она ломает стабильность префикса, на которой стоит replay-guard. По достижении потолка длина фиксируется и `>=` продолжает пропускать апдейты — безопасно, первые 64 KB идентичны. ~~Полный текст всегда доступен через `/events`.~~ ⚠️ **Ревизия 2026-07-29 ([ADR-067](../../adr/ADR-067-agent-run-background-consumer.md)):** формулировка «полный текст всегда доступен через `/events`» была верна для прямого relay и **под broker-моделью неверна** — ring тоже ограничен (`AGENT_RUN_EVENT_BUFFER_MAX`/`..._MAX_BYTES`), ради чего и введён обязательный маркер `run.truncated`. **Полноту текста длинного прогона не гарантирует ни один источник:** `/state.resultText` — 64 KB head-preserving, `/events` — содержимое ring'а текущего поколения. Неполнота при этом **наблюдаема** (маркер), а не молчалива.
- **Все переходы статуса — условные** (`WHERE status IN ('running','resumed')`, [ADR-066 §3](../../adr/ADR-066-agent-run-state-snapshot.md)). Безусловная запись терминального статуса даёт гонку: после `POST /stop` Hermes ещё дофлашивает события, и долетевшее `run.completed`/`run.failed` затёрло бы `cancelled`. Условие делает победителем **первый** терминальный статус и защищает `paused`.
- **`mark_stopped(run_id, user_id)` — только клиентский `POST …/stop`, owner-scoped** (`AND user_id=:uid` в самом `UPDATE` — RBAC становится свойством запроса, а не только предшествующей проверки).** Pause-at-zero ([ADR-064 §3](../../adr/ADR-064-incremental-agent-run-billing-and-pause-resume.md) п.2) дёргает Hermes-interrupt **тем же** `self.stop()`; если пометка статуса окажется внутри общего метода, прогон при исчерпании баланса транзиентно станет `cancelled` → `/state` отдаст `stopped` вместо `paused`, а `POST /resume` в этом окне вернёт `409 run_not_resumable`. Пометка выносится на клиентский путь (после passthrough) либо внутренний interrupt использует отдельный метод без записи статуса.
- **Флаг OFF.** При `agent_incremental_billing_enabled=false` под флагом остаётся **только биллинг**: события `usage.delta` образ шлёт по-прежнему, и relay **накапливает их якоря в снапшот всегда** — токены `/state` двигаются и в этом режиме, а `run.completed` лишь финализирует картину. ⚠️ Прежняя формулировка «событий `usage.delta` нет» **неверна** и противоречила коду, который сознательно ведёт якоря при OFF. Текст/инструменты/approval пишутся как обычно. ⚠️ Форма носителя счётчиков в `run.completed` **не подтверждена** ([Q-067-10](../../99-open-questions.md)); relay читает union носителей и предупреждает при нулевой сумме на непустом блоке.
- ~~**Нет подписчика — нет записи.** Снапшот двигается только пока открыт relay; это же ограничение биллинга ([Q-047-2](../../99-open-questions.md)) — фоновый consumer, закрывающий обе проблемы, отложен ([ADR-066 §8](../../adr/ADR-066-agent-run-state-snapshot.md)).~~ ⚠️ **Ревизия 2026-07-29 → [ADR-067](../../adr/ADR-067-agent-run-background-consumer.md).** Ограничение оказалось не «отставанием снапшота», а **потерей выручки**: без подписчика `run.completed` не обрабатывается, `_mark_terminal` не вызывается, биллинг не финализируется (замер прода: 3 прогона → 0 списаний, `trialRemaining`=1, прогон #1 висел `running` >15 мин — [TD-037](../../100-known-tech-debt.md)). Митигация «повторная подписка довыполнит debit» **неисполнима вдвойне**: она требует действия клиента, которого измеренно не происходит, и — по перемеру 2026-07-30 ([Q-066-1](../../99-open-questions.md) **Closed**) — повторная подписка всё равно не получила бы ни реплея, ни новых событий: поток одноразовый. **Новый инвариант ([ADR-067](../../adr/ADR-067-agent-run-background-consumer.md)):** записи в таблице выше исполняет **фоновый consumer** — единственный upstream-подписчик Hermes, стартующий при `POST /v1/agent/run`/`/resume` и живущий до терминального события; **клиентский `/events` не пишет ничего** (ни снапшота, ни статуса, ни списаний) и читает downstream из Redis. Все правила записи ниже — троттлинг, per-column guard, head-preserving truncation, условность статусов, owner-scoping — переносятся в consumer **дословно**; меняется исполнитель, не правила. Страховка при потере consumer'а — orphan-reaper ([ADR-067 §5](../../adr/ADR-067-agent-run-background-consumer.md)).
- `result_text`/`pending_approval` — **user-content**: пишутся только репозиторием снапшота, в логи/audit не попадают; redaction-контракт ([ADR-049](../../adr/ADR-049-redaction-usage-token-counts-allowlist.md)) не меняется.

## Redaction usage-полей (инвариант + follow-up)
- **Дельта-каунты `input_tokens`/`output_tokens`/`total_tokens`** (обе казинга) — в `_USAGE_COUNT_ALLOWLIST` ([ADR-049](../../adr/ADR-049-redaction-usage-token-counts-allowlist.md), `src/app/observability/redaction.py`): **переживают** redaction (билинг-аналитика, не секрет) везде, где `meta.usage` проходит через `redact()`.
- **Кумулятивные `cumulative_input_tokens`/`cumulative_output_tokens`/`cumulative_total_tokens`** ([ADR-064 §7](../../adr/ADR-064-incremental-agent-run-billing-and-pause-resume.md)) — матчат substring-денилист `token`, но **НЕ** входят в `_USAGE_COUNT_ALLOWLIST`. **Текущий инвариант:** на incremental-пути `meta.usage.cumulative_*` попадают только в `ledger_transactions.meta` (сырой, минуя `redact()`), в тело SSE `usage.delta` (relay as-is) и в admin wallet-view (сырой ledger.meta) — **ни один из этих путей не пропускает их через `redact()`**, поэтому сейчас они не редактируются и сохраняются для реконсиляции. ⚠️ **Латентный риск:** если будущий audit-путь начнёт нести `meta.usage` через `redact()`, `cumulative_*` будут ошибочно вычищены (billing-аналитика потеряна, противоречит принципу [ADR-049](../../adr/ADR-049-redaction-usage-token-counts-allowlist.md)). Defense-in-depth-фикс (расширить allowlist на `cumulative_*`) зафиксирован как **[TD-035](../../100-known-tech-debt.md)** (owner backend). Реальные токен-секреты (`API_SERVER_KEY`/bearer/`x-admin-token`) редактируются как прежде.

## Incremental-биллинг ([ADR-064](../../adr/ADR-064-incremental-agent-run-billing-and-pause-resume.md), флаг `agent_incremental_billing_enabled`)
- На каждом `usage.delta`: `owed = usage_to_credits(cumulative_input, cumulative_output)`; `want = owed − charged`; при `want>0` списать `charge = min(want, balance)` — idempotency `f"{runId}:{stepIndex}"`, `meta.source='agent_run'`+`incremental=true`, commit каждый шаг. Сумма per-step charges **телескопирует точно** в `usage_to_credits(final)` (per-step `ceil` дельт запрещён — инфляция).
- **Seed `charged` из ledger** (reconnect-safe): `charged_for_run` = `SUM(amount)` по debit-строкам `idempotency_key = runId OR LIKE 'runId:%'`, читается в начале `stream_events`.
- **Stop-at-0:** при `charge < want` (баланса не хватило) → `stop(runId)` (Hermes interrupt) + синтетическое `run.paused` + `agent_runs.status='paused'`. **БЕЗ долга** (`charge ≤ balance` → debt-ветка [ADR-051](../../adr/ADR-051-agent-debt-reconciliation.md) недостижима; `netBalance==balance` [ADR-063](../../adr/ADR-063-client-facing-debt-and-net-balance.md)). Сервис поглощает недобор ≤ одного шага ([Q-064-2](../../99-open-questions.md)).
- **Финализация на `run.completed`:** `remainder = usage_to_credits(final) − charged`, при `>0` — debit idempotency `runId` (голый). Paused-прогон финализации не имеет (нет `run.completed`). Флаг OFF: `charged=0` → `remainder=full` = постфактум [ADR-047](../../adr/ADR-047-usage-based-billing-for-agent.md).

## Биллинг на `run.completed`
- `amount = ceil(input_tokens/1000*CREDITS_PER_1K_INPUT + output_tokens/1000*CREDITS_PER_1K_OUTPUT)`; минимум `1` при ненулевом usage; кредиты целые.
- Идемпотентность по `runId` ([ADR-005](../../adr/ADR-005-idempotency-ledger.md)) — повторная подписка/ретрай/дубль события → один debit.
- `usage` сохраняется в `ledger_transactions.meta` (аудит/аналитика), не содержит секретов.
- `audit`-событие `agent_run` + `billing_debit` (без `API_SERVER_KEY`/user-content).
- **Недостаток баланса на финализации `run.completed` ([ADR-047 §6](../../adr/ADR-047-usage-based-billing-for-agent.md) / [ADR-051](../../adr/ADR-051-agent-debt-reconciliation.md)):** ретранслятор НЕ рвёт стрим. Поведение зависит от `AGENT_DEBT_RECONCILE_ENABLED` (дефолт **`true`**):
  - **Дефолт (reconcile ON) — основная ветка ([ADR-051](../../adr/ADR-051-agent-debt-reconciliation.md), `_consume_agent_with_debt`, `wallet/service.py`):** `consume` списывает доступный `balance` (**частичный** ledger-debit) и недобор `delta = amount − balance` кладёт в **`wallets.debt`** (НЕ ledger-строка); audit **`billing_debit_insufficient`** (+ `partialDebited`/`debtAdded`/`debt`). Долг гасится clawback'ом при пополнении; следующий прогон блокируется policy `debt_outstanding` до погашения ([02-api-contracts.md](02-api-contracts.md)). `InsufficientCreditsError` **не** поднимается.
  - **Flag-off / гоночный fallback:** при выключенном флаге (или редкой гонке, когда partial-путь вернул `None` и defer в обычный `_debit_in_savepoint`) `consume` поднимает `InsufficientCreditsError` → savepoint откатывается (**debit не записан, баланс не тронут, orphan-строки нет**), несписанная дельта фиксируется тем же audit `billing_debit_insufficient` — usage не теряется молча.
  - Реконсиляция долга закрыта **[TD-029](../../100-known-tech-debt.md) (ADR-051)**; открытым остаётся только обрыв SSE до `run.completed` — [Q-047-2](../../99-open-questions.md).
  - **NB (incremental-путь, [ADR-064](../../adr/ADR-064-incremental-agent-run-billing-and-pause-resume.md)):** per-step debit долг **не** копит (self-clamp `_consume_incremental_clamp`, `charge≤balance`) → при 0 идёт `run.paused` без долга. Debt-ветка выше применима только к **финализации остатка** на `run.completed` (meta без `incremental`).
- **Usage-каунты НЕ редактируются ([ADR-049](../../adr/ADR-049-redaction-usage-token-counts-allowlist.md)):** `input_tokens`/`output_tokens`/`total_tokens` в payload `billing_debit_insufficient` (и в `agent_run`/`billing_debit`/`ledger.meta.usage`) — целочисленная биллинг-аналитика, НЕ секрет; redaction-allowlist исключает их из `*token*`-денилиста, поэтому usage сохраняется для реконсиляции. Реальные токен-секреты (`API_SERVER_KEY`, `identityToken`, `x-admin-token`, bearer) редактируются как прежде.
