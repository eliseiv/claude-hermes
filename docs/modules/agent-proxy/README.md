# Module: Agent Proxy

- Статус: **Спроектирован, ожидает реализации** (Hermes-интеграция)
- Ответственность: контур `/v1/agent/*` — прокси чата к персональному Hermes-инстансу пользователя (`POST /v1/runs`), ретрансляция SSE-событий на iOS, policy-gate до прогона, биллинг по реальному usage на `run.completed`. Headline-фича сервиса (автономный агент). Простой чат `/v1/chat/*` остаётся отдельно.

## DoD
- `POST /v1/agent/run` — auth ([ADR-044](../../adr/ADR-044-client-api-key-auth.md)) → policy-gate (BR-2/3/5, [ADR-002](../../adr/ADR-002-access-policy-state-machine.md)) → `ensure_running(userId)` ([ADR-046](../../adr/ADR-046-per-user-hermes-runtime.md)) → прокси `POST {base}/v1/runs` (`Authorization: Bearer <API_SERVER_KEY>`) → `202 {runId, status}`. Blocked → `200 {status:blocked, blockReason}` ([ADR-004](../../adr/ADR-004-blocked-http-200.md)).
- `GET /v1/agent/runs/{runId}/events` — SSE-ретрансляция из Hermes; на `run.completed{usage}` → `WalletService.consume(idempotency_key=runId)` (конвертация токенов в кредиты, [ADR-047](../../adr/ADR-047-usage-based-billing-for-agent.md)); `run.failed` → без debit.
- `POST /v1/agent/runs/{runId}/approval`, `POST /v1/agent/runs/{runId}/stop` — passthrough к Hermes.
- **([ADR-064](../../adr/ADR-064-incremental-agent-run-billing-and-pause-resume.md), под флагом `agent_incremental_billing_enabled`)** incremental-биллинг на `usage.delta` (idempotency `runId:step`, cumulative-owed-minus-charged, seed из ledger); pause-at-zero → `run.paused` без долга; финализация остатка на `run.completed` (idempotency `runId`).
- **`POST /v1/agent/runs/{runId}/resume`** ([ADR-064 §5](../../adr/ADR-064-incremental-agent-run-billing-and-pause-resume.md)) — RBAC-404, пред-гвард `status∈{paused,resumed}`→409 `run_not_resumable`, policy-gate (blocked 200), **атомарный CAS `paused→resumed`** (арбитр гонки: конкурентные resume/ретраи → один child; проигравший→active child или `409 resume_in_progress`), hydrate→`conversation_history` (`404`/пусто → `409 session_expired`, откат CAS), `_launch_run` **после** CAS (single-flight)+chain (`agent_runs`), `202 {status:running, runId:new, continuedFrom:old}`.
- **`GET /v1/agent/runs/{runId}/state`** ([ADR-066](../../adr/ADR-066-agent-run-state-snapshot.md)) — снапшот состояния прогона из БД (`agent_runs` + новая `agent_run_snapshots`, миграция `0019`): `{runId, sessionId, status, resultText, lastTool, pendingApproval, blockReason, usage, updatedAt, continuedFrom}`. **Строго read-only** (без `ensure_running`/Hermes/списаний/policy-gate), RBAC-404, `429` по rate-limit. Снапшот пишется **побочным эффектом relay** `/events` (троттлинг `message.delta`, **per-column** replay-guard: длина текста + `GREATEST` по токенам + `pending_approval` через `CASE WHEN :assert_approval` (троттлинговый `message.delta` его не трогает) при безусловных `last_tool`/`updated_at`, head-preserving truncation). Статус `waiting_approval` — производный (`running|resumed` + `pending_approval`), `cancelled` → клиентский `stopped`.
- **Lifecycle-запись `agent_runs` — всегда** ([ADR-066 §3](../../adr/ADR-066-agent-run-state-snapshot.md)): `create_running`/терминальный статус пишутся независимо от `agent_incremental_billing_enabled` (под флагом — только биллинг). Терминальный статус пишет сервисный `_mark_terminal(run_id, status)` (обёртка над репозиторным `mark_status`, commit + проглатывание `SQLAlchemyError`) **до** биллинга и независимо от его исхода (отказ списания больше не оставляет прогон вечно `running`); `mark_stopped(run_id, user_id)` и `clear_pending_approval(run_id, user_id)` — owner-scoped. Начинают выставляться `failed` (на `run.failed`) и `cancelled` (после 2xx клиентского `POST /stop`) — ранее не записывались никогда. **Все** переходы статуса условные (`WHERE status IN ('running','resumed')`), `mark_stopped(run_id, user_id)` — только клиентский путь (внутренний interrupt pause-at-zero статус не помечает).
- **Фоновый consumer + broker `/events`** ([ADR-067](../../adr/ADR-067-agent-run-background-consumer.md), **спроектировано, ожидает реализации**) — к Hermes подключается **ровно один потребитель, наш consumer** (стартует при `POST /v1/agent/run`/`/resume`, до отдачи `202`); он исполняет биллинг, снапшот-writer и `_mark_terminal` **независимо от присутствия клиента**. Клиентский `GET …/events` — **читающий downstream** (Redis ring + pub/sub); миграция — только `0020` (heartbeat-колонка). Закрывает измеренную утечку выручки ([TD-037](../../100-known-tech-debt.md), [Q-047-2](../../99-open-questions.md)). Обоснование **не зависит от поведения образа** ([ADR-067 §0](../../adr/ADR-067-agent-run-background-consumer.md)).
- ⚠️ **Требует согласования с iOS:** форма событий не меняется, но **каждое соединение `/events` самодостаточно и начинается с реплея с начала прогона** ([ADR-067 §3.4](../../adr/ADR-067-agent-run-background-consumer.md)) — клиент обязан сбрасывать накопленный текст, иначе удвоит его. Плюс **пять правил закрытия стрима** (§3.3): раньше его закрывал сам Hermes.
- **Живучесть:** heartbeat consumer'а в отдельной колонке `agent_run_snapshots.consumer_heartbeat_at` (вне Redis, не протекает в клиентский `updatedAt`); детектор смерти upstream — **транспортный** (TCP keep-alive; idle-таймаут по молчанию запрещён); единственный временной ограничитель — продуктовый потолок длительности прогона; orphan-reaper с fail-closed проверкой `INFO server → uptime` и потолком финализаций на тик (§5). Kill-switch `AGENT_RUN_CONSUMER_ENABLED` ([TD-038](../../100-known-tech-debt.md)).
- **Внешние допущения** — таблица в [ADR-067](../../adr/ADR-067-agent-run-background-consumer.md). ✅ **H1/H2/H4 закрыты перемером 2026-07-30:** поток событий прогона **одноразовый** (историю получает первый подписчик, повторная подписка инертна даже на живом прогоне) ⇒ adoption и ретрай подписки **невозможны**, orphan-reaper — единственный и постоянный путь доводки, порядок «consumer раньше клиента» — требование корректности. Открытыми остаются **H3** (объём orphan-reaper), **H5**, **H7** (верхняя граница §6.5), **H8** (форма `run.completed` — деньги), **H9**.
- **Неподтверждённые формы событий образа** (капча `tests/fixtures/hermes_prod_run_adr065.sse` их не содержит — прогон шёл при нулевом балансе и без инструментов): **[Q-067-10](../../99-open-questions.md)** — форма `usage` в `run.completed`, **денежный путь** (при флаге OFF это единственное списание прогона, промах = бесплатный прогон; владелец добычи — devops/qa); **[Q-067-11](../../99-open-questions.md)** — формы `tool.*`/`approval.request`, путь снапшота/UI. Провенанс капчи и правило «фикстуры внешних интеграций — только с первоисточника» — [06-testing-strategy.md](../../06-testing-strategy.md), [09-testing.md](09-testing.md).
- **Открытые вопросы фичи:** [Q-067-12](../../99-open-questions.md) (drain-режим деплоя — рестарт `api` под прогоном необратимо теряет биллинговый хвост), [Q-067-4](../../99-open-questions.md) (**несёт ли hydrate usage/токены — проверить ДО Phase 9**, меняет объём orphan-reaper'а), [Q-067-2](../../99-open-questions.md) (лимит одновременных прогонов), [Q-067-3](../../99-open-questions.md) (маркер усечения ring), [Q-066-3](../../99-open-questions.md) (`continuedTo`). **Partially Closed:** [Q-066-1](../../99-open-questions.md) (закрыто сырое наблюдение «вторая последовательная подписка = 0 байт»; интерпретация «дренаж» — гипотеза H1, ждёт перемера с критерием живости). **Closed 2026-07-29:** [Q-066-2](../../99-open-questions.md) (`run_id` = `run_` + 32 hex, ~128 бит ⇒ глобальная уникальность валидна; tenancy-гвард остаётся как defense-in-depth), charset-часть [Q-064-4](../../99-open-questions.md) (⚠️ LIKE-экранирование снимать нельзя — префикс `run_` содержит `_`).
- **Retention** снапшота — `AGENT_RUN_SNAPSHOT_TTL_DAYS` (14): у терминальных прогонов чистится только `result_text`/`pending_approval`, строка и `/state` остаются; sweep идемпотентен и `updated_at` не двигает.

Долг заведён, потому что это **ровно тот класс, что вычищался весь раздел**: свойство подменено доступным поблизости числом, из-за чего тюнинг TTL lease **молча** меняет задержку закрытия клиентского стрима. Решение: свой knob `AGENT_RUN_SUBSCRIBER_PROBE_SECONDS` + fail-fast инвариант «срок пробы < период»; при `0.5 с` сцена на срок пробы становится дешёвой и устойчивой (сейчас зазор `7 с` против `10 с` — кандидат во флейк). **(5) Методический вывод 4 в [06-testing-strategy.md](../../06-testing-strategy.md): «ассерт, который не может упасть, хуже отсутствующего — и это бывает свойством окружения».** Отсутствующий ассерт виден в обзоре, а неспособный упасть выглядит покрытием и создаёт доверие, которого не заслуживает; когда причина в окружении, таких ассертов сразу **класс**. Два обязательных следствия: ассерт на наблюдаемость принимается **только с мутацией, которая его роняет**; прежде чем чинить «недоходящий» сигнал — проверить, доходит ли до него **исполнение**.

Дополнительно назван **четвёртый вид записи в baseline — сброс в `0`** (две точки: событийная ветка и периодическая): провенанс он не портит, но обнуляет знание об отданном, поэтому обязан объявляться — случай C, а не A. **Инвариант переписан:** «отбрасывать только уже отданное» **неисполнимо** скалярным baseline (`delivered` — **верхняя метка**, а не множество `seq`), и ревьюер построил достижимый случай **после** [TD-047](../../100-known-tech-debt.md) — событие, вытесненное из ring'а обрезкой, приходит в дырку **ниже** метки и гасится как «доказанный дубль». Принята **строгая** версия: сессия помнит **`replay_min_seq`**, и `event.seq < replay_min_seq` — **разрыв**, а не дубль; цена — один скаляр, выгода — инвариант становится **проверяемым ассертом**, а не описанием намерений (иначе qa выбирал бы между «ослабить тест» и «счесть корректный код дефектным»). **Границы правила «всегда маркер»:** `?afterSeq=0` — **исключение без маркера** (нулевой курсор пуст и тождествен отсутствию, парный негатив в тестах сохранён); маркер непринятого курсора несёт **`seq = 0`** и **не двигает** baseline — иначе клиент запомнил бы `id: <epoch>-500` и переподключался бы с отвергнутым курсором, то есть отказ стал бы **самоподдерживающимся**. **Клиентский контракт разведён на две ветки везде, где был склеен** (это документ, уходящий в iOS, а согласование §3.4 открыто): [02-api-contracts.md](02-api-contracts.md) — таблица поведения клиента разбита на `Last-Event-ID` / `?afterSeq>0` / `?afterSeq=0`; в ADR — строка §3.4 для `afterSeq`, правило для клиента п. 1 («поддержать заголовок **или** параметр — и больше ничего не нужно» ⇒ для параметра **всегда** включается п. 3), снятая гарантия «действителен только для текущего поколения» помечена как **неисполнимая**, и пункт §Consequences про инкрементальный реконнект больше не числит `afterSeq` улучшением без оговорки. **Мелкое:** S2 определён как **максимум** `seq`, а не «последний элемент списка», с названной зависимостью от атомарности Lua (§3.1). ✅ **Ревьюер перебрал оси и нового входа в молчащий стрим не построил — первый такой раунд;** найденная им дырка ниже метки — молчащая потеря **одиночного** события, и инвариант теперь покрывает и её.

Новые допущения: **H5** (покрытие `timestamp` по типам событий, [Q-067-7](../../99-open-questions.md)) и **H6** ([Q-067-6](../../99-open-questions.md)). **Третья ревизия (по третьему architect-review):** новые механизмы внесли новые блокеры, оба закрыты. (1) **Курсор `seq` не переживал перезапуск Redis** — ring и счётчик стираются, `INCR` идёт с 1, lease **живой** (правила закрытия не срабатывают), старый курсор отбрасывает все новые события ⇒ навсегда открытый **молчащий** стрим, хуже заменяемого поведения. Курсор сделан **самоидентифицирующим**: `id: <epoch>-<seq>`, несовпадение поколения ⇒ пустой курсор ⇒ полный реплей + `run.truncated`. Доспецифицирован контракт: пустой курсор ≡ `0` (маркер усечения работает и на первом подключении), приоритет `Last-Event-ID` над `?afterSeq=`, `afterSeq: int ≥ 0` иначе `400`. (2) **Живость была самозаявлением consumer'а:** при зависании нашей обработки (блокирующая запись в БД, дедлок) сокет и пир живы, независимые петли lease/heartbeat продолжали бы отмечаться, а таймер `MAX_DURATION` внутри зависшей корутины не сработал бы. Введено структурное требование: consumer — **рабочая задача + супервизор**, heartbeat и lease **производны от прогресса** (beacon `awaiting_upstream`/`processing`), зависание дольше `AGENT_RUN_PROCESSING_STALL_SECONDS` снимает lease и отменяет рабочую задачу, `MAX_DURATION` применяется **отменой** извне. (3) **Гибель супервизора не останавливала рабочую задачу** — новый способ ложно финализировать работающий прогон: reaper ставит `failed` и списывает по неполному кумулятиву, штатная финализация отбрасывается как дубль по тому же ключу, `_mark_terminal('completed')` — no-op ⇒ прогон навсегда `failed`.
