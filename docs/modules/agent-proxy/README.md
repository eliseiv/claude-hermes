# Module: Agent Proxy

- Статус: **Спроектирован, ожидает реализации** (Hermes-интеграция)
- Ответственность: контур `/v1/agent/*` — прокси чата к персональному Hermes-инстансу пользователя (`POST /v1/runs`), ретрансляция SSE-событий на iOS, policy-gate до прогона, биллинг по реальному usage на `run.completed`. Headline-фича сервиса (автономный агент). Простой чат `/v1/chat/*` остаётся отдельно.

## DoD
- `POST /v1/agent/run` — auth ([ADR-044](../../adr/ADR-044-client-api-key-auth.md)) → policy-gate (BR-2/3/5, [ADR-002](../../adr/ADR-002-access-policy-state-machine.md)) → `ensure_running(userId)` ([ADR-046](../../adr/ADR-046-per-user-hermes-runtime.md)) → прокси `POST {base}/v1/runs` (`Authorization: Bearer <API_SERVER_KEY>`) → `202 {runId, status}`. Blocked → `200 {status:blocked, blockReason}` ([ADR-004](../../adr/ADR-004-blocked-http-200.md)).
- `GET /v1/agent/runs/{runId}/events` — SSE-ретрансляция из Hermes; на `run.completed{usage}` → `WalletService.consume(idempotency_key=runId)` (конвертация токенов в кредиты, [ADR-047](../../adr/ADR-047-usage-based-billing-for-agent.md)); `run.failed` → без debit.
- `POST /v1/agent/runs/{runId}/approval`, `POST /v1/agent/runs/{runId}/stop` — passthrough к Hermes.
- **([ADR-064](../../adr/ADR-064-incremental-agent-run-billing-and-pause-resume.md), под флагом `agent_incremental_billing_enabled`)** incremental-биллинг на `usage.delta` (idempotency `runId:step`, cumulative-owed-minus-charged, seed из ledger); pause-at-zero → `run.paused` без долга; финализация остатка на `run.completed` (idempotency `runId`).
- **`POST /v1/agent/runs/{runId}/resume`** ([ADR-064 §5](../../adr/ADR-064-incremental-agent-run-billing-and-pause-resume.md)) — RBAC-404, пред-гвард `status∈{paused,resumed}`→409 `run_not_resumable`, policy-gate (blocked 200), **атомарный CAS `paused→resumed`** (арбитр гонки: конкурентные resume/ретраи → один child; проигравший→active child или `409 resume_in_progress`), hydrate→`conversation_history` (`404`/пусто → `409 session_expired`, откат CAS), `_launch_run` **после** CAS (single-flight)+chain (`agent_runs`), `202 {status:running, runId:new, continuedFrom:old}`.
- **`GET /v1/agent/runs/{runId}/state`** ([ADR-066](../../adr/ADR-066-agent-run-state-snapshot.md)) — снапшот состояния прогона из БД (`agent_runs` + новая `agent_run_snapshots`, миграция `0019`): `{runId, sessionId, status, resultText, lastTool, pendingApproval, blockReason, usage, updatedAt, continuedFrom}`. **Строго read-only** (без `ensure_running`/Hermes/списаний/policy-gate), RBAC-404, `429` по rate-limit. Снапшот пишется **побочным эффектом relay** `/events` (троттлинг `message.delta`, **per-column** replay-guard: длина текста + `GREATEST` по токенам + `pending_approval` через `CASE WHEN :assert_approval` (троттлинговый `message.delta` его не трогает) при безусловных `last_tool`/`updated_at`, head-preserving truncation). Статус `waiting_approval` — производный (`running|resumed` + `pending_approval`), `cancelled` → клиентский `stopped`.
- **Lifecycle-запись `agent_runs` — всегда** ([ADR-066 §3](../../adr/ADR-066-agent-run-state-snapshot.md)): `create_running`/терминальный статус пишутся независимо от `agent_incremental_billing_enabled` (под флагом — только биллинг). Терминальный статус пишет сервисный `_mark_terminal(run_id, status)` (обёртка над репозиторным `mark_status`, commit + проглатывание `SQLAlchemyError`) **до** биллинга и независимо от его исхода (отказ списания больше не оставляет прогон вечно `running`); `mark_stopped(run_id, user_id)` и `clear_pending_approval(run_id, user_id)` — owner-scoped. Начинают выставляться `failed` (на `run.failed`) и `cancelled` (после 2xx клиентского `POST /stop`) — ранее не записывались никогда. **Все** переходы статуса условные (`WHERE status IN ('running','resumed')`), `mark_stopped(run_id, user_id)` — только клиентский путь (внутренний interrupt pause-at-zero статус не помечает).
- **Фоновый consumer + broker `/events`** ([ADR-067](../../adr/ADR-067-agent-run-background-consumer.md), **спроектировано, ожидает реализации**) — к Hermes подключается **ровно один потребитель, наш consumer** (стартует при `POST /v1/agent/run`/`/resume`, до отдачи `202`); он исполняет биллинг, снапшот-writer и `_mark_terminal` **независимо от присутствия клиента**. Клиентский `GET …/events` — **читающий downstream** (Redis ring + pub/sub); миграция — только `0020` (heartbeat-колонка). Закрывает измеренную утечку выручки ([TD-037](../../100-known-tech-debt.md), [Q-047-2](../../99-open-questions.md)). Обоснование **не зависит от поведения образа** ([ADR-067 §0](../../adr/ADR-067-agent-run-background-consumer.md)).
- ⚠️ **Требует согласования с iOS:** форма событий не меняется, но **каждое соединение `/events` самодостаточно и начинается с реплея с начала прогона** ([ADR-067 §3.4](../../adr/ADR-067-agent-run-background-consumer.md)) — клиент обязан сбрасывать накопленный текст, иначе удвоит его. Плюс **пять правил закрытия стрима** (§3.3): раньше его закрывал сам Hermes.
- **Живучесть:** heartbeat consumer'а в отдельной колонке `agent_run_snapshots.consumer_heartbeat_at` (вне Redis, не протекает в клиентский `updatedAt`); детектор смерти upstream — **транспортный** (TCP keep-alive; idle-таймаут по молчанию запрещён); единственный временной ограничитель — продуктовый потолок длительности прогона; orphan-reaper с fail-closed проверкой `INFO server → uptime` и потолком финализаций на тик (§5). Kill-switch `AGENT_RUN_CONSUMER_ENABLED` ([TD-038](../../100-known-tech-debt.md)).
- **Внешние допущения** — таблица в [ADR-067](../../adr/ADR-067-agent-run-background-consumer.md). ✅ **H1/H2/H4 закрыты перемером 2026-07-30:** поток событий прогона **одноразовый** (историю получает первый подписчик, повторная подписка инертна даже на живом прогоне) ⇒ adoption и ретрай подписки **невозможны**, orphan-reaper — единственный и постоянный путь доводки, порядок «consumer раньше клиента» — требование корректности. Открытыми остаются **H3** (объём orphan-reaper), **H5**, **H7** (верхняя граница §6.5), **H8** (форма `run.completed` — деньги), **H9**.
- **Неподтверждённые формы событий образа** (капча `tests/fixtures/hermes_prod_run_adr065.sse` их не содержит — прогон шёл при нулевом балансе и без инструментов): **[Q-067-10](../../99-open-questions.md)** — форма `usage` в `run.completed`, **денежный путь** (при флаге OFF это единственное списание прогона, промах = бесплатный прогон; владелец добычи — devops/qa); **[Q-067-11](../../99-open-questions.md)** — формы `tool.*`/`approval.request`, путь снапшота/UI. - 2026-07-30 (7): **Фикс [TD-040](../../100-known-tech-debt.md) отражён в docs** (architect, по итогам второй итерации backend). **Клиентски-видимое:** в [02-api-contracts.md](02-api-contracts.md) заведён раздел **§Коды 502** для `POST /v1/agent/run`, `/resume`, `/stop`, `/approval` — различение **`upstream_timeout`** (инстанс **промолчал**: дедлайн фазы HTTP, readiness cold-start/wake, сквозной бюджет, ожидание row-lock) vs **`upstream_error`** (инстанс **отказал**: refused/reset/DNS/протокол, Hermes 5xx, либо исход определён). Оценка верна только при разведённой connect-фазе, которая теперь обеспечена. Записан урок: **стоимость ретрая обязана включать стоимость попытки, а не только паузу между попытками**; неограниченная попытка превращает ретрай из смягчения отказа в его умножение. Поведенческий сдвиг (медленный connect >10 с не ретраится, а падает) признан приемлемым внутри `hermes-net`, с оговоркой пересматривать при смене сетевой топологии. **Заведён [TD-041](../../100-known-tech-debt.md):** вызовы docker-демона (`containers.run`/`start` через docker-py в `asyncio.to_thread`) **вне бюджета** и принципиально неотменяемы — остаточная дыра в гарантии TD-040. Порядок починки **не переставляем**: сначала реконсиляция по имени контейнера (`containers.get(spec.name)` перед `run`), потом таймаут — голый таймаут делает отказ **вечным** (`409` по занятому имени, т.к. `_replay_stale_provisioning` удаляет только `if row.container_id`). **Заведён [Q-056-3](../../99-open-questions.md)** (продуктовый): оставлять ли `HERMES_PROVISION_READY_TIMEOUT_SECONDS=90` — единственный оставшийся источник больших чисел (потолок бюджета 150 выведен из него) — или переводить launch на **асинхронный контур** (`202` сразу, wake в фоне, готовность через `/state`), что для мобильного клиента принципиально лучше, но пересекается с [ADR-067](../../adr/ADR-067-agent-run-background-consumer.md). ⚠️ **TD-040 НЕ закрыт** — ждёт прод-подтверждения devops после деплоя (DoD внешних контрактов).

Новые допущения: **H5** (покрытие `timestamp` по типам событий, [Q-067-7](../../99-open-questions.md)) и **H6** ([Q-067-6](../../99-open-questions.md)). **Третья ревизия (по третьему architect-review):** новые механизмы внесли новые блокеры, оба закрыты. (1) **Курсор `seq` не переживал перезапуск Redis** — ring и счётчик стираются, `INCR` идёт с 1, lease **живой** (правила закрытия не срабатывают), старый курсор отбрасывает все новые события ⇒ навсегда открытый **молчащий** стрим, хуже заменяемого поведения. Курсор сделан **самоидентифицирующим**: `id: <epoch>-<seq>`, несовпадение поколения ⇒ пустой курсор ⇒ полный реплей + `run.truncated`. Доспецифицирован контракт: пустой курсор ≡ `0` (маркер усечения работает и на первом подключении), приоритет `Last-Event-ID` над `?afterSeq=`, `afterSeq: int ≥ 0` иначе `400`. (2) **Живость была самозаявлением consumer'а:** при зависании нашей обработки (блокирующая запись в БД, дедлок) сокет и пир живы, независимые петли lease/heartbeat продолжали бы отмечаться, а таймер `MAX_DURATION` внутри зависшей корутины не сработал бы. Введено структурное требование: consumer — **рабочая задача + супервизор**, heartbeat и lease **производны от прогресса** (beacon `awaiting_upstream`/`processing`), зависание дольше `AGENT_RUN_PROCESSING_STALL_SECONDS` снимает lease и отменяет рабочую задачу, `MAX_DURATION` применяется **отменой** извне. Также: heartbeat-запись — **отдельным `UPDATE` одной колонки** (иначе апсерт двигал бы `updated_at` и обесценил миграцию `0020`); третий индекс по heartbeat **отменён** в пользу самоочищающегося `ix_agent_runs_active` на `agent_runs` (ревизия «двух индексов» [ADR-066 §7](../../adr/ADR-066-agent-run-state-snapshot.md) отмечена явно); keep-alive конкретизирован до `socket_options` (у `httpx` knob'а нет, Linux-дефолт 7200 с делал детектор фиктивным); снято утверждение «полный текст всегда доступен через `/events`» — под broker-моделью полноту не гарантирует ни один источник; `MAX_DURATION` вынесен в **[Q-067-8](../../99-open-questions.md)**, keep-alive — в **[Q-067-9](../../99-open-questions.md)**; описан флип kill-switch при активных прогонах. **Четвёртая ревизия:** (1) **`epoch` проверялся только при открытии стрима** — у уже подключённого клиента дефект сохранялся целиком (перезапуск Redis → consumer жив, lease не истекает, правила закрытия не срабатывают, новые события отбрасываются как «уже отданные» → молчащий стрим до конца прогона). `epoch` сделан свойством **читающей сессии**: кладётся в элементы ring'а и сообщения канала, сверяется на событии / при восстановлении pub/sub / периодически; при несовпадении — сброс курсора и `run.truncated`. (3) **Гибель супервизора не останавливала рабочую задачу** — новый способ ложно финализировать работающий прогон: reaper ставит `failed` и списывает по неполному кумулятиву, штатная финализация отбрасывается как дубль по тому же ключу, `_mark_terminal('completed')` — no-op ⇒ прогон навсегда `failed`. Клиент с `Last-Event-ID` получает инкрементальный реконнект (ломающего изменения нет); клиент без курсора — полный реплей и обязан сбрасывать текст ([ADR-067 §3.4](../../adr/ADR-067-agent-run-background-consumer.md)). **Миграция `0020`** (колонка `consumer_heartbeat_at` + самоочищающийся индекс `ix_agent_runs_active` на `agent_runs`). **Также зафиксирована фактическая форма `message.delta`** ([05-events.md](05-events.md)): поле **`delta` со значением-строкой** (не объект с `.text`) — расхождение docs↔образ дало `resultText` тождественно пустым и сделало непригодным дискриминатор замера [Q-066-1](../../99-open-questions.md); фикс — **backend, раньше остального** (без него перемер невозможен).
