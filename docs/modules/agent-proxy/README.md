# Module: Agent Proxy

- Статус: **Спроектирован, ожидает реализации** (Hermes-интеграция)
- Ответственность: контур `/v1/agent/*` — прокси чата к персональному Hermes-инстансу пользователя (`POST /v1/runs`), ретрансляция SSE-событий на iOS, policy-gate до прогона, биллинг по реальному usage на `run.completed`. Headline-фича сервиса (автономный агент). Простой чат `/v1/chat/*` остаётся отдельно.

## DoD
- `POST /v1/agent/run` — auth ([ADR-044](../../adr/ADR-044-client-api-key-auth.md)) → policy-gate (BR-2/3/5, [ADR-002](../../adr/ADR-002-access-policy-state-machine.md)) → `ensure_running(userId)` ([ADR-046](../../adr/ADR-046-per-user-hermes-runtime.md)) → прокси `POST {base}/v1/runs` (`Authorization: Bearer <API_SERVER_KEY>`) → `202 {runId, status}`. Blocked → `200 {status:blocked, blockReason}` ([ADR-004](../../adr/ADR-004-blocked-http-200.md)).
- `GET /v1/agent/runs/{runId}/events` — SSE-ретрансляция из Hermes; на `run.completed{usage}` → `WalletService.consume(idempotency_key=runId)` (конвертация токенов в кредиты, [ADR-047](../../adr/ADR-047-usage-based-billing-for-agent.md)); `run.failed` → без debit.
- `POST /v1/agent/runs/{runId}/approval`, `POST /v1/agent/runs/{runId}/stop` — passthrough к Hermes.
- **([ADR-064](../../adr/ADR-064-incremental-agent-run-billing-and-pause-resume.md), под флагом `agent_incremental_billing_enabled`)** incremental-биллинг на `usage.delta` (idempotency `runId:step`, cumulative-owed-minus-charged, seed из ledger); pause-at-zero → `run.paused` без долга; финализация остатка на `run.completed` (idempotency `runId`).
- **`POST /v1/agent/runs/{runId}/resume`** ([ADR-064 §5](../../adr/ADR-064-incremental-agent-run-billing-and-pause-resume.md)) — RBAC-404, пред-гвард `status∈{paused,resumed}`→409 `run_not_resumable`, policy-gate (blocked 200), **атомарный CAS `paused→resumed`** (арбитр гонки: конкурентные resume/ретраи → один child; проигравший→active child или `409 resume_in_progress`), hydrate→`conversation_history` (`404`/пусто → `409 session_expired`, откат CAS), `_launch_run` **после** CAS (single-flight)+chain (`agent_runs`), `202 {status:running, runId:new, continuedFrom:old}`.
- **`GET /v1/agent/runs/{runId}/state`** ([ADR-066](../../adr/ADR-066-agent-run-state-snapshot.md)) — снапшот состояния прогона из БД (`agent_runs` + новая `agent_run_snapshots`, миграция `0019`): `{runId, sessionId, status, resultText, lastTool, pendingApproval, blockReason, usage, updatedAt, continuedFrom}`. **Строго read-only** (без `ensure_running`/Hermes/списаний/policy-gate), RBAC-404, `429` по rate-limit. Снапшот пишется **побочным эффектом relay** `/events` (троттлинг `message.delta`, **per-column** replay-guard: длина текста + `GREATEST` по токенам + `pending_approval` через `CASE WHEN :assert_approval` (троттлинговый `message.delta` его не трогает) при безусловных `last_tool`/`updated_at`, head-preserving truncation). Статус `waiting_approval` — производный (`running|resumed` + `pending_approval`), `cancelled` → клиентский `stopped`.
- **Lifecycle-запись `agent_runs` — всегда** ([ADR-066 §3](../../adr/ADR-066-agent-run-state-snapshot.md)): `create_running`/терминальный статус пишутся независимо от `agent_incremental_billing_enabled` (под флагом — только биллинг). Терминальный статус пишет сервисный `_mark_terminal(run_id, status)` (обёртка над репозиторным `mark_status`, commit + проглатывание `SQLAlchemyError`) **до** биллинга и независимо от его исхода (отказ списания больше не оставляет прогон вечно `running`); `mark_stopped(run_id, user_id)` и `clear_pending_approval(run_id, user_id)` — owner-scoped. Начинают выставляться `failed` (на `run.failed`) и `cancelled` (после 2xx клиентского `POST /stop`) — ранее не записывались никогда. **Все** переходы статуса условные (`WHERE status IN ('running','resumed')`), `mark_stopped(run_id, user_id)` — только клиентский путь (внутренний interrupt pause-at-zero статус не помечает).
- **Фоновый consumer + broker `/events`** ([ADR-067](../../adr/ADR-067-agent-run-background-consumer.md), **спроектировано, ожидает реализации**) — к Hermes подключается **ровно один потребитель, наш consumer** (стартует при `POST /v1/agent/run`/`/resume`, до отдачи `202`); он исполняет биллинг, снапшот-writer и `_mark_terminal` **независимо от присутствия клиента**. Клиентский `GET …/events` — **читающий downstream** (Redis ring + pub/sub); миграция — только `0020` (heartbeat-колонка). Закрывает измеренную утечку выручки ([TD-037](../../100-known-tech-debt.md), [Q-047-2](../../99-open-questions.md)). Обоснование **не зависит от поведения образа** ([ADR-067 §0](../../adr/ADR-067-agent-run-background-consumer.md)).
- ⚠️ **Требует согласования с iOS:** форма событий не меняется, но **каждое соединение `/events` самодостаточно и начинается с реплея с начала прогона** ([ADR-067 §3.4](../../adr/ADR-067-agent-run-background-consumer.md)) — клиент обязан сбрасывать накопленный текст, иначе удвоит его. Плюс **пять правил закрытия стрима** (§3.3): раньше его закрывал сам Hermes.
- **Живучесть:** heartbeat consumer'а в отдельной колонке `agent_run_snapshots.consumer_heartbeat_at` (вне Redis, не протекает в клиентский `updatedAt`); детектор смерти upstream — **транспортный** (TCP keep-alive; idle-таймаут по молчанию запрещён); единственный временной ограничитель — продуктовый потолок длительности прогона; orphan-reaper с fail-closed проверкой `INFO server → uptime` и потолком финализаций на тик (§5). Kill-switch `AGENT_RUN_CONSUMER_ENABLED` ([TD-038](../../100-known-tech-debt.md)).
- **Внешние допущения** — таблица в [ADR-067](../../adr/ADR-067-agent-run-background-consumer.md). ✅ **H1/H2/H4 закрыты перемером 2026-07-30:** поток событий прогона **одноразовый** (историю получает первый подписчик, повторная подписка инертна даже на живом прогоне) ⇒ adoption и ретрай подписки **невозможны**, orphan-reaper — единственный и постоянный путь доводки, порядок «consumer раньше клиента» — требование корректности. Открытыми остаются **H3** (объём orphan-reaper), **H5**, **H7** (верхняя граница §6.5), **H8** (форма `run.completed` — деньги), **H9**.
- **Неподтверждённые формы событий образа** (капча `tests/fixtures/hermes_prod_run_adr065.sse` их не содержит — прогон шёл при нулевом балансе и без инструментов): **[Q-067-10](../../99-open-questions.md)** — форма `usage` в `run.completed`, **денежный путь** (при флаге OFF это единственное списание прогона, промах = бесплатный прогон; владелец добычи — devops/qa); **[Q-067-11](../../99-open-questions.md)** — формы `tool.*`/`approval.request`, путь снапшота/UI. Провенанс капчи и правило «фикстуры внешних интеграций — только с первоисточника» — [06-testing-strategy.md](../../06-testing-strategy.md), [09-testing.md](09-testing.md).
- **Открытые вопросы фичи:** [Q-067-12](../../99-open-questions.md) (drain-режим деплоя — рестарт `api` под прогоном необратимо теряет биллинговый хвост), [Q-067-4](../../99-open-questions.md) (**несёт ли hydrate usage/токены — проверить ДО Phase 9**, меняет объём orphan-reaper'а), [Q-067-2](../../99-open-questions.md) (лимит одновременных прогонов), [Q-067-3](../../99-open-questions.md) (маркер усечения ring), [Q-066-3](../../99-open-questions.md) (`continuedTo`). **Partially Closed:** [Q-066-1](../../99-open-questions.md) (закрыто сырое наблюдение «вторая последовательная подписка = 0 байт»; интерпретация «дренаж» — гипотеза H1, ждёт перемера с критерием живости). **Closed 2026-07-29:** [Q-066-2](../../99-open-questions.md) (`run_id` = `run_` + 32 hex, ~128 бит ⇒ глобальная уникальность валидна; tenancy-гвард остаётся как defense-in-depth), charset-часть [Q-064-4](../../99-open-questions.md) (⚠️ LIKE-экранирование снимать нельзя — префикс `run_` содержит `_`).
- **Retention** снапшота — `AGENT_RUN_SNAPSHOT_TTL_DAYS` (14): у терминальных прогонов чистится только `result_text`/`pending_approval`, строка и `/state` остаются; sweep идемпотентен и `updated_at` не двигает.
- Маппинг тела `message→input`, `sessionId→session_id`, `model→model`; `effective_session_id = sessionId or uuid4()` пишется в `agent_runs`.
- `/v1/chat/*` не затронут; Hermes в `LLMClient.create_message` не заводится.

## Changelog
- 2026-07-30 (3): **Шестое ревью ADR-067 — текстовые правки, дизайн не менялся** (architect). (1) §Consequences обещал, что «H1 разблокирует adoption и ретрай», хотя H1 закрыта, а сами возможности объявлены **постоянно** невозможными — перечень открытых гипотез приведён к реальному (H3/H7/H8/H9/H10) с явной пометкой, что adoption и ретрай установленной подписки — свойство архитектуры, а не отложенная возможность. (2) ⚠️ **Снято неверное load-bearing утверждение** «при ложной H10 ретрай бесполезен, но не вреднее текущего поведения»: наиболее вероятный подслучай — ретрай **успешно устанавливается транспортно**, инертен только поток; тогда beacon в `awaiting_upstream` (по §6.1 «живы» безусловно), lease и heartbeat обновляются, и прогон уходит к reaper'у по `MAX_DURATION` (2 ч) вместо 15 минут, удерживая инстанс от гибернации — дословно тот вред, которым обоснован запрет ретрая в случае (1). Решение: connect-only retry **специфицирован, но включается только после замера** ([Q-067-13](../../99-open-questions.md) — предусловие Phase 9), флаг `AGENT_RUN_CONSUMER_CONNECT_RETRY_ENABLED` с дефолтом `false`; структурный guard на инертную подписку (`bytes_read == 0` ⇒ beacon `connecting`) записан как follow-up **с требованием замера порога** ([Q-067-6](../../99-open-questions.md)), чтобы не повторить ошибку idle-таймаута. (3) **H4** («первый подписчик получает историю») понижена до «согласуется с наблюдением, отдельной пробой не упражнялась» — процедура перемера её не проверяла (момент открытия первой подписки относительно первых событий не зафиксирован); последствий нет, guard и так defense-in-depth. (4) В [ADR-066](../../adr/ADR-066-agent-run-state-snapshot.md) (§8-маркер и таблица §Ревизия) дописано, что формулировка «параллельный consumer физически невозможен» была снята 2026-07-29 как недоказанная и **восстановлена 2026-07-30 на другом основании** — прямом замере односторонности потока, а не через H2. (5) В [Q-067-12](../../99-open-questions.md) к варианту «(г) вынести consumer в отдельный процесс» добавлены две неочевидные статьи цены: где живут orphan-свип и retention-sweep [ADR-066 §7](../../adr/ADR-066-agent-run-state-snapshot.md) (чтобы не задвоились и не исчезли) и переезд удержания инстанса от гибернации — новый процесс получает доступ к таблицам [Hermes Runtime](../hermes-runtime/README.md).
- 2026-07-30 (2): **Пятое ревью ADR-067 — исправлены расхождения внутри документа** (architect). ⚠️ **Главное:** §Context и §0 оставались от прошлой редакции и **противоречили остальному ADR** — там значилось «Статус H1: не подтверждена и не опровергнута» и «ADR принимается до перемеров», тогда как §1/§9/§Alternatives уже ссылались на перемер как на источник доказанного. Причина сбоя: рерайт §Context был подготовлен, но потерялся — скрипт правок упал на позднейшей проверке **до записи файла**, а следующий прогон делал только остальные замены. §Context переписан в «Факт 2 (измерено 2026-07-30, прогоны `run_b170a402…`, `run_cfda1890…`)» с указанием устранённого конфаундера живости; §0 п. 4 — «исход измерен и подтвердил необходимость broker'а» вместо «устойчивость к обоим исходам». **Содержательная правка:** постоянный запрет ретрая подписки был **шире измеренного** — замер говорит о **второй** подписке, после потребления потока, а отказ на **connect**-фазе означает, что образ подписчика не видел, и повторная попытка станет **первой** подпиской. Введён §6.4.1: два случая — обрыв установленной подписки (запрет навсегда) vs connect-only retry по образцу [ADR-062](../../adr/ADR-062-wake-readiness-gate-and-connect-only-launch-retry.md) (явный кортеж `ConnectError`/`ConnectTimeout`/`PoolTimeout`, те же `HERMES_LAUNCH_RETRY_*`). Цена ошибки асимметрична: без подписчика прогон **бесплатен навсегда** ([TD-037](../../100-known-tech-debt.md)). Из событийного пайплайна §3.1 убран `SET epoch … NX` (ключ создаётся один раз при старте вместе с lease) — иначе признак «ключа `epoch` нет» был бы неоднозначным, а на нём стоят §3.2 и §3.3 п. 3.

Принят **курсор реконнекта** (`Last-Event-ID`/`?afterSeq=` поверх уже имевшегося `seq`, SSE-поле `id:`) — реконнект стал инкрементальным, и для клиента со стандартной SSE-библиотекой изменение **перестало быть ломающим**; **`run.truncated` переведён из отложенных в обязательные** (иначе сброс текста молча заменял бы полный текст на обрезанный). Redis-grace операционализирован через `INFO server → uptime_in_seconds` (fail-closed) вместо неоперационализуемого «времени текущего соединения»; per-tick cap уточнён как **на воркер**; персистенция Redis подлежит **отключению** (класс данных ring'а шире снапшота, TTL не ограничивает RDB и бэкапы). `AGENT_RUN_MAX_DURATION_SECONDS` явно помечен **продуктовым** ограничением. Новые допущения: **H5** (покрытие `timestamp` по типам событий, [Q-067-7](../../99-open-questions.md)) и **H6** ([Q-067-6](../../99-open-questions.md)). **Третья ревизия (по третьему architect-review):** новые механизмы внесли новые блокеры, оба закрыты. (1) **Курсор `seq` не переживал перезапуск Redis** — ring и счётчик стираются, `INCR` идёт с 1, lease **живой** (правила закрытия не срабатывают), старый курсор отбрасывает все новые события ⇒ навсегда открытый **молчащий** стрим, хуже заменяемого поведения. Курсор сделан **самоидентифицирующим**: `id: <epoch>-<seq>`, несовпадение поколения ⇒ пустой курсор ⇒ полный реплей + `run.truncated`. Доспецифицирован контракт: пустой курсор ≡ `0` (маркер усечения работает и на первом подключении), приоритет `Last-Event-ID` над `?afterSeq=`, `afterSeq: int ≥ 0` иначе `400`. (2) **Живость была самозаявлением consumer'а:** при зависании нашей обработки (блокирующая запись в БД, дедлок) сокет и пир живы, независимые петли lease/heartbeat продолжали бы отмечаться, а таймер `MAX_DURATION` внутри зависшей корутины не сработал бы. Введено структурное требование: consumer — **рабочая задача + супервизор**, heartbeat и lease **производны от прогресса** (beacon `awaiting_upstream`/`processing`), зависание дольше `AGENT_RUN_PROCESSING_STALL_SECONDS` снимает lease и отменяет рабочую задачу, `MAX_DURATION` применяется **отменой** извне. Также: heartbeat-запись — **отдельным `UPDATE` одной колонки** (иначе апсерт двигал бы `updated_at` и обесценил миграцию `0020`); третий индекс по heartbeat **отменён** в пользу самоочищающегося `ix_agent_runs_active` на `agent_runs` (ревизия «двух индексов» [ADR-066 §7](../../adr/ADR-066-agent-run-state-snapshot.md) отмечена явно); keep-alive конкретизирован до `socket_options` (у `httpx` knob'а нет, Linux-дефолт 7200 с делал детектор фиктивным); снято утверждение «полный текст всегда доступен через `/events`» — под broker-моделью полноту не гарантирует ни один источник; `MAX_DURATION` вынесен в **[Q-067-8](../../99-open-questions.md)**, keep-alive — в **[Q-067-9](../../99-open-questions.md)**; описан флип kill-switch при активных прогонах. **Четвёртая ревизия:** (1) **`epoch` проверялся только при открытии стрима** — у уже подключённого клиента дефект сохранялся целиком (перезапуск Redis → consumer жив, lease не истекает, правила закрытия не срабатывают, новые события отбрасываются как «уже отданные» → молчащий стрим до конца прогона). `epoch` сделан свойством **читающей сессии**: кладётся в элементы ring'а и сообщения канала, сверяется на событии / при восстановлении pub/sub / периодически; при несовпадении — сброс курсора и `run.truncated`. (2) **Beacon обновлялся после итерации**, из-за чего самое вероятное зависание («итерация закончилась → пришло событие → обработчик завис») не детектировалось бы **никогда**: `processing` теперь выставляется **перед** входом в обработку, добавлены монотонные счётчики прогресса и состояние `connecting` (не свободное от лимита). (3) **Гибель супервизора не останавливала рабочую задачу** — новый способ ложно финализировать работающий прогон: reaper ставит `failed` и списывает по неполному кумулятиву, штатная финализация отбрасывается как дубль по тому же ключу, `_mark_terminal('completed')` — no-op ⇒ прогон навсегда `failed`. Обе задачи переведены в общую `TaskGroup`. Также: `needs_code_sync` приведён в соответствие с индексом `ix_agent_runs_active` (ведущий столбец `created_at`); `epoch` создаётся вместе с lease; описано, что при `AGENT_RUN_CONSUMER_ENABLED=false` прогоны окна остаются `running` навсегда; введена fail-fast валидация `AGENT_RUN_MAX_DURATION_SECONDS > 0`. **Дизайн-дыры, закрытые в первой ревизии:** правила **закрытия клиентского стрима** (терминальное событие может не появиться в Redis никогда — раньше стрим закрывал Hermes); **ограничители жизни consumer'а** (idle-upstream + потолок длительности — без них зависший consumer вечно продлевает lease и исключает прогон из reaper'а); **heartbeat в `agent_runs.updated_at` вне Redis** + redis-grace и per-tick cap в orphan-свипе (перезапуск Redis стирает все lease разом); **правило при обрыве своей upstream-подписки** (самозавершение без ретрая); `seq` из Redis `INCR`; `EXPIRE` ring'а в каждом пайплайне; **байтовый потолок ring'а**; `maxmemory-policy noeviction`. **Контракт:** форма событий сохраняется; добавлены SSE-поле `id:` и `run.truncated`. Клиент с `Last-Event-ID` получает инкрементальный реконнект (ломающего изменения нет); клиент без курсора — полный реплей и обязан сбрасывать текст ([ADR-067 §3.4](../../adr/ADR-067-agent-run-background-consumer.md)). **Миграция `0020`** (колонка `consumer_heartbeat_at` + самоочищающийся индекс `ix_agent_runs_active` на `agent_runs`). **Также зафиксирована фактическая форма `message.delta`** ([05-events.md](05-events.md)): поле **`delta` со значением-строкой** (не объект с `.text`) — расхождение docs↔образ дало `resultText` тождественно пустым и сделало непригодным дискриминатор замера [Q-066-1](../../99-open-questions.md); фикс — **backend, раньше остального** (без него перемер невозможен).
