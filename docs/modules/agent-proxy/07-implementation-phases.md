# Agent Proxy — Implementation Phases

Соответствует Спринтам 1/3/4 плана Hermes-интеграции ([ADR-045](../../adr/ADR-045-hermes-as-agent-proxy.md), [ADR-047](../../adr/ADR-047-usage-based-billing-for-agent.md)). Зависит от [Hermes Runtime](../hermes-runtime/07-implementation-phases.md) (Спринт 2). **Phase 6/7 — incremental billing + pause + resume ([ADR-064](../../adr/ADR-064-incremental-agent-run-billing-and-pause-resume.md), под флагом, требует патча образа Hermes). Phase 8 — снапшот состояния прогона + `GET …/state` ([ADR-066](../../adr/ADR-066-agent-run-state-snapshot.md), без флага, патча образа НЕ требует).**

## Phase 2 — Контракт и схемы

## Phase 3 — run + policy + ensure_running
- `POST /v1/agent/run`: policy-gate (`PolicyEngine.evaluate`, blocked → `200`) → `HermesInstanceManager.ensure_running` → прокси `POST /v1/runs` (`Authorization: Bearer <api_key>`) → `202 {runId}`.
- Маппинг тела (`message→input` и т.д.).
- Обработка ошибок инстанса (`502`).

## Phase 4 — SSE + биллинг ([ADR-047](../../adr/ADR-047-usage-based-billing-for-agent.md))
- `GET /v1/agent/runs/{runId}/events` — SSE-ретрансляция; парсинг событий ([05-events.md](05-events.md)).
- На `run.completed.usage` → `WalletService.consume(idempotency_key=runId)`; конвертация токенов (`CREDITS_PER_1K_*`, ceil, мин. 1).
- `run.failed` → без debit. Audit `agent_run`/`billing_debit`.
- `POST .../approval`, `POST .../stop` — passthrough.

## Phase 5 — Config + интеграция
- `CREDITS_PER_1K_INPUT`/`CREDITS_PER_1K_OUTPUT` в config ([07-deployment.md](../../07-deployment.md)).

## Phase 6 — Incremental billing + pause-at-zero ([ADR-064](../../adr/ADR-064-incremental-agent-run-billing-and-pause-resume.md) §1–§4, под флагом `agent_incremental_billing_enabled`)
- Предусловие: **патч образа Hermes** — событие `usage.delta` (`cumulative_*_tokens`, `step_index`) — **devops/Hermes-зона** (пересборка образа + digest).
- `src/app/config.py` — `agent_incremental_billing_enabled` (default OFF).
- Таблица `agent_runs` + enum + миграция `0018` (`src/app/models/tables.py`, `migrations/versions/…0018_agent_runs.py`); `src/app/agent_proxy/runs_repo.py` (create_running/get/record_step/mark_paused/mark_status/active_child).
- `src/app/wallet/service.py` — `charged_for_run` (SUM по `runId OR runId:%`, `ESCAPE '\'`) + `_consume_incremental_clamp` (маршрутизация по `meta.incremental` **до** `_debit_in_savepoint`; `LEAST(:amount,balance)`, без raise/без debt).
- `src/app/agent_proxy/service.py` — incremental billing в `stream_events` (seed `charged`, per-step `_bill_step`+commit, `if charge>0`), pause-at-zero `_pause_run` (stop + синтетическое `run.paused`), финализация остатка в `_bill_completed` (idempotency `runId`), корневая строка `agent_runs` в `run()` + `effective_session_id`.

## Phase 7 — Resume (continuation) ([ADR-064](../../adr/ADR-064-incremental-agent-run-billing-and-pause-resume.md) §5)
- `src/app/schemas/agent.py` — `AgentResumeRequest{message?}` + `AgentRunResponse.continuedFrom`.
- `src/app/api_gateway/routers/agent.py` — `POST /v1/agent/runs/{runId}/resume`.
- `service.py resume()` — RBAC-404 → пред-гвард → policy-gate (blocked 200) → **атомарный CAS `paused→resumed`** (арбитр гонки) → ветвление (winner: ensure_running→hydrate→_launch_run **после** CAS→chain `create_running(continued_from)`; loser/ретрай: active child → `202`/`409 resume_in_progress`) → reconcile-откат CAS на сбое.
- Hydrate `_fetch_session_transcript` (`GET {base}/api/sessions/{session_id}/messages`) → `conversation_history`.

## Phase 8 — Снапшот состояния прогона + `/state` ([ADR-066](../../adr/ADR-066-agent-run-state-snapshot.md))
Порядок этапов обязателен: каждый следующий опирается на предыдущий, первые два ценны и без эндпоинта.

1. **Схема.** `AgentRunSnapshot` в `src/app/models/tables.py` + миграция `migrations/versions/…0019_agent_run_snapshots.py` (expand-only, по образцу `0018`; `down_revision="0018_agent_runs"`, single head; DDL — [03-data-model.md §25](../../03-data-model.md)). Новый `src/app/agent_proxy/snapshots_repo.py`: upsert `ON CONFLICT (run_id) DO UPDATE` с **per-column** replay-guard (`CASE` по `char_length` для `result_text`, `GREATEST` для токенов, `CASE WHEN :assert_approval` для `pending_approval`, безусловный `EXCLUDED.*` для `last_tool`/`updated_at`; отдельный owner-scoped `clear_pending_approval(run_id, user_id)` под `POST …/approval` — **row-level `WHERE` запрещён**, [ADR-066 §6](../../adr/ADR-066-agent-run-state-snapshot.md)) + **идемпотентный** retention-sweep (guard `AND (result_text <> '' OR pending_approval IS NOT NULL)`, `updated_at` не трогается) под **частичный** индекс `ix_agent_run_snapshots_sweep`; owner-scoped `get(run_id, user_id)`/`clear_pending_approval(run_id, user_id)` + tenancy-гвард `WHERE t.user_id = EXCLUDED.user_id` в апсерте. DI в `src/app/deps.py`. Три настройки в `src/app/config.py` ([07-deployment.md](../../07-deployment.md)).
2. **Lifecycle-фиксы** ([ADR-066 §3](../../adr/ADR-066-agent-run-state-snapshot.md)) — **независимы от эндпоинта**: снять флаговый guard с `create_running` (корневой прогон + resume-child) и с записи терминального статуса. **Все переходы статуса — условные** `UPDATE … WHERE status IN ('running','resumed')` (в т.ч. `completed`/`failed`, иначе долетевшее после `/stop` терминальное событие затрёт `cancelled`). Терминальный статус пишет единый `_mark_terminal(run_id, status)` (прежний `_mark_completed` удалён), вызываемый в обработчике `run.completed`/`run.failed` **до** биллинга и независимо от его исхода — иначе отказ списания оставляет прогон вечно `running`. Новый owner-scoped `runs_repo.mark_stopped(run_id, user_id)` (`AND user_id=:uid`) вызывается **только** на клиентском пути после 2xx `POST /stop`; внутренний interrupt pause-at-zero (тот же `self.stop()`, [ADR-064 §3](../../adr/ADR-064-incremental-agent-run-billing-and-pause-resume.md)) его **не** выполняет — иначе пауза транзиентно станет `cancelled` и сломает `/state` + `/resume`. Биллинг (`record_step`, per-step debits, pause-at-zero, финализация, resume) остаётся под `agent_incremental_billing_enabled`.
3. **Снапшот-writer в relay** (`stream_events`): вынести накопление `partial_text`/`steps`/токенов из ветки `if incremental:`; апсерты по событиям с явным `commit()` — правила и троттлинг в [05-events.md §Снапшот-побочные эффекты](05-events.md); расширить набор обрабатываемых событий на `approval.request`; очистка `pending_approval` также в `approval()` после 2xx — через `snapshots_repo.clear_pending_approval(run_id, user_id)`, а не апсертом. Сервисная обёртка `_mark_terminal(run_id, status)` вызывает репозиторный `mark_status` (условный переход), коммитит и проглатывает `SQLAlchemyError` — сбой записи статуса не рвёт стрим. `preview` в `_build_pending_approval()` обрезается тем же `AGENT_STATE_RESULT_TEXT_MAX_CHARS`.
4. **Эндпоинт** `GET /v1/agent/runs/{runId}/state` в `src/app/api_gateway/routers/agent.py` + `AgentProxyService.get_state(user_id, run_id)`; схемы `AgentRunStateResponse`/`AgentPendingApproval` в `src/app/schemas/agent.py` (StrictModel, camelCase, русские descriptions); чистая функция маппинга статусов ([02-api-contracts.md](02-api-contracts.md)). **Read-only инварианты зафиксировать в docstring роута:** без `ensure_running`, без обращения к Hermes, без списаний, без policy-gate. OpenAPI responses `200`/`401`/`404`/`429` с примерами ([08-api-documentation.md §R5](../../08-api-documentation.md)).
5. **Retention** — sweep в существующем reaper-цикле по `AGENT_RUN_SNAPSHOT_TTL_DAYS` ([ADR-066 §7](../../adr/ADR-066-agent-run-state-snapshot.md)); может отгружаться последним.

## Phase 9 — Фоновый consumer + broker `/events` ([ADR-067](../../adr/ADR-067-agent-run-background-consumer.md))

**Зачем:** прогон без подписчика на `/events` не тарифицируется и вечно висит `running` — измерено на проде (3 прогона → 0 списаний, `trialRemaining`=1, статус `running` >15 мин): [TD-037](../../100-known-tech-debt.md), severity **high**, влияет на выручку. **Миграция `0020`** (одна колонка `agent_run_snapshots.consumer_heartbeat_at` + частичный индекс). Форма событий сохраняется; добавляются SSE-поле `id:` (курсор реконнекта) и синтетическое `run.truncated` — для клиента со стандартной SSE-библиотекой ломающим изменением это не является ([ADR-067 §3.4](../../adr/ADR-067-agent-run-background-consumer.md)).

**Предусловия (выполнить ДО этой фазы):**
- **Фикс парсинга `message.delta`** (поле `delta` — строка, [05-events.md](05-events.md)). Без него `resultText` пуст и перемер [Q-066-1](../../99-open-questions.md) невозможен. Owner: **backend**, вне Phase 9.
- ⚠️ **[Q-067-4](../../99-open-questions.md) (hydrate/usage) — БОЛЬШЕ НЕ предусловие.** Замер недостижим через публичный API (эндпоинт на internal-адресе инстанса, generic-passthrough нет) и требует отдельного канала (SSH `.156`). Реализацию это **не блокирует**: orphan-reaper спроектирован на best-effort финализацию по последнему наблюдённому кумулятиву снапшота и самодостаточен. **Условным остаётся только объём п. 5** — при подтверждённом «hydrate несёт токены» доводка сможет тарифицировать точнее и в режиме `agent_incremental_billing_enabled=false`, где сейчас из снапшота брать нечего.
- ✅ **[Q-067-13](../../99-open-questions.md) закрыт (H10 опровергнута)** — connect-retry удалён из дизайна, предусловия больше нет.
- **Согласование §3.4 с iOS** — поддержать `Last-Event-ID`/`?afterSeq=` (тогда реконнект инкрементален и делать больше нечего) либо сбрасывать накопленный текст при каждом новом соединении; обработать `run.truncated`.
- **Продуктовое согласование `AGENT_RUN_MAX_DURATION_SECONDS`** (2 ч) — это видимое пользователю ограничение «прогон длиннее 2 часов принудительно прекращается» ([ADR-067 §6](../../adr/ADR-067-agent-run-background-consumer.md)), а не технический предохранитель.

Порядок этапов обязателен.

0. **Миграция `0020`** — `agent_run_snapshots.consumer_heartbeat_at TIMESTAMPTZ NULL` (⚠️ `first_byte_at` **отменена** вместе с §5.1) + частичный индекс **`ix_agent_runs_active`** на `agent_runs` (`(created_at) WHERE status IN ('running','resumed')` — ведущий столбец `created_at`, т.к. возраст считается по `COALESCE(consumer_heartbeat_at, created_at)`) ([03-data-model.md §25](../../03-data-model.md)); `down_revision="0019_agent_run_snapshots"`, expand-only, single head. Колонка клиенту **не отдаётся**. ⚠️ Индекса по `consumer_heartbeat_at` **не заводить** — он не самоочищается и рос бы со всей историей; состав индексов `agent_run_snapshots` остаётся два ([ADR-066 §7](../../adr/ADR-066-agent-run-state-snapshot.md)).
1. **Транспорт (Redis).** Ключи в отдельной логической БД `AGENT_RUN_REDIS_DB`: `…:events` (LIST), `…:pub` (канал), `…:lease`, `…:seq`, **`…:epoch`** (создаётся **при старте consumer'а вместе с lease**, не первым событием), **`…:bytes`** (running-счётчик размера ring'а — без него байтовый потолок неисполним: пересчёт `O(ring)` до 8 МБ на событие либо счётчик в памяти воркера, врущий после перехвата lease). **`epoch` кладётся в каждый элемент ring'а и каждое сообщение канала.** **Запись события — Lua-скриптом** (не клиентским pipeline: нужна атомарность относительно перехвата lease, иначе порядок элементов ring'а разойдётся с порядком `seq` и сломает дедуп broker'а): `INCR seq` → `RPUSH` → `INCRBY bytes` → **цикл `LPOP` + `DECRBY bytes`** по **двум** потолкам (`AGENT_RUN_EVENT_BUFFER_MAX` и `AGENT_RUN_EVENT_BUFFER_MAX_BYTES`) — ⚠️ **`LTRIM` не годится**: он не сообщает, что удалил, и байтовый счётчик нельзя удержать с ним в согласии → **`EXPIRE` events/seq/epoch/bytes** → `PUBLISH`. ⚠️ **Самое новое событие не выбрасывается никогда**, даже если одно превышает потолок (иначе ring пуст и клиент не видит ни события, ни причины); неполнота наблюдаема через `run.truncated`. ⚠️ `EXPIRE` — **в каждом** пайплайне, иначе ring исчезнет посреди длинного прогона; `seq` — **только Redis `INCR`**, не счётчик в памяти воркера; **`epoch` обязателен** — без него курсор не переживает перезапуск Redis и клиент получает навсегда открытый молчащий стрим ([ADR-067 §3.1](../../adr/ADR-067-agent-run-background-consumer.md)). Запись — **best-effort**: ошибка Redis логируется и не прерывает consumer. Сопутствующая настройка Redis: явный `maxmemory` + `maxmemory-policy noeviction` ([05-security.md](../../05-security.md)). **22 настройки** в `src/app/config.py` ([07-deployment.md](../../07-deployment.md); 22-я — **`AGENT_RUN_SUBSCRIBER_DRAIN_SECONDS`**, [ADR-067 §3.2.2](../../adr/ADR-067-agent-run-background-consumer.md)) + **9 инвариантов fail-fast** (девятый — **`AGENT_RUN_SUBSCRIBER_DRAIN_SECONDS > 0`**): `budget >= ready + 2 × proxy` ([TD-040](../../100-known-tech-debt.md)); `MAX_DURATION > 0`; `HEARTBEAT < ORPHAN_TIMEOUT`; `ORPHAN_REDIS_GRACE > LEASE_RENEW`; `LEASE_RENEW < LEASE_TTL`; `AGENT_RUN_REDIS_DB` ≠ БД из `REDIS_URL`; **`SHUTDOWN_DRAIN > 0`**; **`HANDSHAKE_TIMEOUT > 0`**. ⚠️ Соотношение `SHUTDOWN_DRAIN < --graceful-timeout` (30 с) **автоматически не проверяется** — graceful-timeout задаётся CLI-флагом, а не env; держится на prod-checklist. ⛔ **НЕ заводить:** `AGENT_RUN_ORPHAN_INSTANCE_RESET_ENABLED` и `AGENT_RUN_INSTANCE_RESET_COOLDOWN_SECONDS` (отменены вместе с §5.1), `AGENT_RUN_CONSUMER_IDLE_TIMEOUT_SECONDS` (idle-таймаут отозван).
2. **Consumer** (`src/app/agent_proxy/consumer.py`) — **две задачи** ([ADR-067 §6.1](../../adr/ADR-067-agent-run-background-consumer.md)):
   - **рабочая:** взять lease → подписаться на `GET {base}/v1/runs/{runId}/events` → на каждое событие пайплайн из п. 1, затем доменная обработка; вести in-memory beacon **на переходах** (`processing` — **перед** входом в обработку, `awaiting_upstream` — перед ожиданием чтения, `connecting` — при установке соединения) + монотонные `bytes_read`/`last_published_seq`. **Доменная обработка — перенос из `stream_events` без изменения правил:** снапшот-writer ([ADR-066 §6](../../adr/ADR-066-agent-run-state-snapshot.md)), `_mark_terminal` **до** биллинга, incremental/постфактум биллинг, pause-at-zero. Транспорт: `socket_options` с `SO_KEEPALIVE`+`TCP_KEEPIDLE`/`TCP_KEEPINTVL`/`TCP_KEEPCNT`, **read-timeout стрима `None`**;
   - **супервизор** (в общей `TaskGroup` с рабочей — **гибель/отмена любой отменяет вторую**): продление lease, heartbeat в `agent_run_snapshots.consumer_heartbeat_at` **отдельным `UPDATE` одной колонки** (апсерт запрещён — двигает `updated_at`), **пока выполняется правило живости §6.1** — ⚠️ **НЕ «только при подтверждённом прогрессе»**: счётчики обязательны лишь для правила «крутящийся цикл», иначе длинный tool-call (агент думает 20 мин) остановил бы heartbeat и свип финализировал бы **живой** прогон; продление lease **трёхзначное** (`RENEWED`/`REACQUIRED` с переустановкой `epoch`/`LOST`, §4); `MAX_DURATION` — **через отмену** рабочей задачи; детект зависания (`processing` дольше `AGENT_RUN_PROCESSING_STALL_SECONDS` → прекратить heartbeat, снять lease, отменить рабочую задачу). Строка снапшота создаётся **при старте**, а не лениво; `hermes_instances.last_active_at` обновляется вместе с heartbeat'ом.
   ⚠️ **Lease — трёхзначный в ОБЕИХ операциях ([ADR-067 §4.1](../../adr/ADR-067-agent-run-background-consumer.md), ревизия 2026-07-31):** взятие → `ACQUIRED`/`HELD_ELSEWHERE`/`UNKNOWN`, продление → `RENEWED`/`REACQUIRED`/`LOST`/`UNKNOWN`. Уход **только** при **чужом** владельце ключа; при `RedisError` прогон ведётся **без lease**. ⛔ **Правка одного взятия без продления запрещена** — прогон был бы убит на первом тике продления, уже потребив одноразовый поток. ⚠️ `prepare_consumer_snapshot` — **внутри** `try/finally` §6.4 ([TD-043](../../100-known-tech-debt.md)).
   ⚠️ **Idle-таймаут по доменным событиям запрещён** (отозван); **heartbeat в `agent_runs.updated_at` запрещён** (отозван). Единый порядок самозавершения — §6.4, шаг «снять lease и heartbeat» обязателен даже при неуспехе финального флаша.
3. **Старт consumer'а** в `service.run()` и `service.resume()` — сразу после успешного `_launch_run`, **до** отдачи `202`. ⚠️ **Порядок относительно `create_running` — [ADR-067 §6.1.2](../../adr/ADR-067-agent-run-background-consumer.md):** `_launch_run` → `create_running` + audit → **коммит** → ожидание handshake → `202`. ⛔ **Ждать handshake ДО `create_running` ЗАПРЕЩЕНО:** с момента, когда `POST {base}/v1/runs` вернул `202`, прогон существует на инстансе и тратит токены, а orphan-reaper (§5) отбирает кандидатов **из `agent_runs`** — прогон без строки не добьёт **никто** (строго хуже [TD-037](../../100-known-tech-debt.md)). Ожидание идёт **после коммита**, без открытой транзакции и удержанного коннекта, и ограничено `AGENT_RUN_HANDSHAKE_TIMEOUT_SECONDS` (15 с, **не** `FIRST_BYTE_STALL`); истечение **не фатально** — `202` отдаётся, audit, consumer живёт дальше. Milestone — сразу после `2xx`, **до** первого события. ⚠️ **Жизнеобеспечение задачи — [ADR-067 §6.1.1](../../adr/ADR-067-agent-run-background-consumer.md):** сессия БД берётся **по операции** (одна долгоживущая на прогон **запрещена** — пул нормирован, а число одновременных прогонов не ограничено; плюс инвариант **не удерживать сессию через `await` на upstream** — прямой урок [TD-040](../../100-known-tech-debt.md)); задача цепляется к **реестру в `lifespan`**, fire-and-forget **запрещён** (задача без ссылки может быть собрана GC, а §6.4 при остановке воркера некому запустить) (требование **гарантии старта**: поток одноразовый, и если consumer не встанет, историю не заберёт никто; конкурировать с клиентом не за что — клиентский `/events` к Hermes не ходит). Нераспарсенное сообщение канала — `warning` (без содержимого), отброшенный доказанный дубль — `debug`;
   - ⛔ **§3.2.1 ([TD-046](../../100-known-tech-debt.md)) — САМЫЙ приоритетный пункт этапа: единственный вход, не требующий отказа инфраструктуры.** Воспроизведено qa на реальном Redis: `?afterSeq=500` при читаемом поколении и максимуме `seq` `3` даёт **пустой открытый стрим** одним HTTP-запросом. Обязательно: **(1)** клиентский курсор **НЕ инициализирует** baseline дедупа (`delivered` стартует нулём, растёт только из отдачи), курсор — **фильтр реплея**; **(2)** числовой гард `cursor.seq > current_seq(run_id)` ⇒ курсор пустой (первый вызов `current_seq` в `src/` — сейчас их **ноль**); **(3)** курсор без `epoch` (`?afterSeq=` **всегда**) принимается только вместе с `run.truncated`; **(4)** маркер порождается **в `stream()`**, а не в `_replay_blocks`, иначе при пустом/отфильтрованном наборе не отдаётся вовсе; **(5)** маркер непринятого курсора несёт **`seq = 0`** и **не двигает** baseline (иначе клиент запомнит `id: <epoch>-500` и будет переподключаться с отвергнутым курсором); **(6)** ⛔ **исключение: `?afterSeq=0` маркера НЕ даёт** — нулевой курсор пуст и тождествен отсутствию, правило «всегда маркер» действует при `afterSeq > 0`; **(7)** сессия помнит **`replay_min_seq`** и трактует `event.seq < replay_min_seq` как **разрыв**, а не дубль (событие, вытесненное из ring'а обрезкой, приходит в дырку ниже верхней метки); ⛔ **(8) контроль непрерывности ВПЕРЁД (ось C2, новая мера):** при `delivered > 0` и `event.seq > delivered + 1` → маркер и отдать — сегодня скачок вперёд проходит молча, а это единственное клиентское оповещение для нераспарсенного/потерянного сообщения канала (лог им не является); ⛔ **(9) маркер по первому отданному в сессии (ось C3):** первый отданный `seq` > фильтр + 1 ⇒ маркер, **независимо от фазы** (реплей или live) — снимает особое правило «при пустом курсоре маркера нет», которое давало **молчащий пропуск начала прогона** при усыновлении с непрочитанным ring'ом;
   - ⛔ **§3.2 шаг 1 ([TD-047](../../100-known-tech-debt.md)):** фактический `SUBSCRIBE` — **до** `LRANGE` (сегодня наоборот, и подписка ленивая); иначе событие в окне теряется **молча**, а мутация дискриминатора `arrived`/`delivered` инертна; каждое событие сопровождать SSE-полем **`id: <epoch>-<seq>`**. Курсор: `Last-Event-ID` приоритетнее `?afterSeq=` (`int ≥ 0`, невалидное → `400`; невалидный заголовок → пустой курсор); **несовпадение `epoch` или `seq` из будущего → курсор пустой**. Backpressure `AGENT_RUN_SUBSCRIBER_QUEUE_MAX` → **отключить подписчика**, consumer не трогать. ⛔ **Измерять ГЛУБИНУ ОЧЕРЕДИ, а не размер всплеска ([ADR-067 §3.2.2](../../adr/ADR-067-agent-run-background-consumer.md), [TD-048](../../100-known-tech-debt.md)):** задача-читатель непрерывно вычитывает канал в явную `asyncio.Queue(maxsize=…)`, отдающая сторона осушает, `QueueFull` ⇒ осознанное отключение. **Запрещено** считать сообщения между пустыми опросами канала — в этом числе скорость клиента не участвует, и оно отключает **быстрого здорового** клиента, не отключая **медленного**. Приёмка — близнецы на `600` событиях при пороге `500`. ⛔ **Классификация — ДО очереди:** в очередь кладётся только причитающееся клиенту (события + маркеры), дубли перекрытия отбрасываются до неё. Иначе `QueueFull` наступает на канальных копиях уже отданных событий (наблюдение qa), а после [TD-047](../../100-known-tech-debt.md) это **штатный** путь: ring `5000` против глубины `500` ⇒ отключение на каждом реконнекте к полному ring'у. Побочно отдающая сторона становится чистым писателем — это же требование (5) режима D2. ⛔ **Ось D (обязательна вместе с мерой, иначе она вносит новый отказ), ДВА режима:** **D1 «умерло»** — сильная ссылка на задачу-читателя, отмена в `finally` с подпиской, **завершение по любой причине закрывает клиентский стрим** (**правило закрытия 6** §3.3); ⛔ **отменяемость за ограниченное время** (D1 требование 2): в задачах горячего пути **запрещены** `asyncio.shield`, `except CancelledError` без немедленного `raise`, `except BaseException`, bare `except:` — иначе `TaskGroup.__aexit__` при отключении клиента ждёт детей неограниченно и **вешает `aclose()`**, утекая задачей обработчика; появится законная нужда в `shield` — тем же изменением приходит ограниченный по времени выход из группы; **D2 «зависло»** — **предельный срок у каждого `await` в цикле доставки** либо **вынос периодических проверок** (`_is_terminal`, `lease_alive`) с пути доставки: сегодня предела нет (`DB_POOL_TIMEOUT` — только ожидание из пула, `statement_timeout`/`lock_timeout` не заданы, [Q-067-20](../../99-open-questions.md)), и это тот же класс, что [TD-040](../../100-known-tech-debt.md). ⛔ **Устройство сессии — ТРИ задачи** (симметрично §6.1); ⚠️ **группировка НЕ обязана быть `TaskGroup`:** при отключении клиента `GeneratorExit` (это `BaseException`) перебрасывается `__aexit__` завёрнутым, и `aclose()` **бросает** вместо возврата — путь штатный, тест красный. Заменяющая конструкция обязана предъявить **четыре** свойства: **teardown возвращается**, **отмена завершается за ограниченное время**, **исключение звена отменяет остальные**, **нормальное завершение звена НЕ отменяет остальные** (два последних давала группа): **читатель** (`SUBSCRIBE` → `LRANGE` → классификация §3.2.1 → очередь), **писатель** (`get` → запись), **супервизор** (периодические проверки правил 4/5 + idle). Реплей — **в читателе**, иначе он классифицирует с `delivered = 0` и отдаёт клиенту всё перекрытие **вторым экземпляром**. ⛔ **Проверки правил 4/5 в читателя — ЗАПРЕЩЕНО** (молчащий стрим при трёх живых задачах). ⛔ **Мера «подтверждение подписки» СНЯТА** — кросс-задачного окна больше нет; от [TD-047](../../100-known-tech-debt.md) остаются порядок внутри читателя и запрет ленивой подписки. ⛔ **Завершение разведено:** штатное — **флаг «штатный конец» СНАЧАЛА, затем sentinel** в зарезервированном слоте; писатель решает **по флагу** (не по содержимому очереди — `peek` в `asyncio.Queue` нет), осушает и отдаёт терминальное событие, потом EOF. Аварийное (`QueueFull`, смерть читателя, D2-таймаут, супервизор) — `Event`/отмена **вне** очереди, очередь бросается **немедленно**. ⚠️ Единым сигналом это делать нельзя: `FIRST_COMPLETED` вправе выбрать `Event` и закрыть стрим **без** `run.completed`. ⛔ **Флага НЕДОСТАТОЧНО — нужны ДВА несущих механизма:** флаг «штатный конец» (писатель различает пути) **и отступ супервизора, пока идёт причитающаяся выдача** — предикат **из двух конъюнктов**: `not queue.empty()` **И** последняя отданная порция свежее `AGENT_RUN_SUBSCRIBER_DRAIN_SECONDS` (состояние пишет **писатель**, перепроверка **после** probe, отступ — **пропуск тика**, не выход из цикла; `settled` **снят полностью**). ⚠️ Снять любой конъюнкт нельзя: без первого правило 5 не срабатывает вовсе (замер — таймаут `15 с` против прежних `~2 с`), без второго заглушение бессрочно при замолчавшем клиенте — иначе у прогона, **терминального на открытии**, правило 4 истинно с первой секунды, а флаг появляется только когда читатель **закончил**, и супервизор бросает очередь посреди реплея. ⛔ **Признак — именно ПРОГРЕСС:** отступ «по знанию читателя» (терминален при открытии / событие в реплее / положено в live) неполон **по построению** — терминальность пишет consumer в БД, и супервизор видит её раньше, чем событие дойдёт по каналу; а **бессрочный** отступ выключает правила 4/5 навсегда, вместе с наблюдаемостью `AGENT_RUN_MAX_DURATION_SECONDS`. Нет прогресса дольше срока ⇒ правила 4/5 **возвращаются**. **Отмена супервизора — необязательная оптимизация**, выполняется **без `await`** на отменённой задаче. ⛔ **Срок ограничивает ОДНО ОЖИДАНИЕ** — отсчёт от последнего успешного прогресса, иначе теряется ровно последний, терминальный блок. ⛔ **Переход в live — по гистерезису:** дисциплина реплея держится, пока `qsize()` не упадёт до `AGENT_RUN_SUBSCRIBER_QUEUE_MAX / 2` — иначе успешный реплей кончается отключением, потому что на границе фаз очередь полна по построению. ⛔ **Бюджет — два независимых срока от одного значения** (реплей+гистерезис у читателя, осушение у писателя); общий счётчик запрещён. ⛔ **Перед `LRANGE` — дождаться ПОДТВЕРЖДЕНИЯ подписки** (не только `create_task`), ленивая подписка запрещена; [TD-048](../../100-known-tech-debt.md) и [TD-047](../../100-known-tech-debt.md) делать одним изменением либо TD-047 первым. Инвариант для C1a: **один читатель, один потребитель, FIFO**. ⛔ **Порядок ветвей обработки сообщения — `C4 > C1a > C1b > C2`, максимум один маркер на сообщение**, эффект на `delivered` у C1a (обнулить) и C1b (сохранить) **противоположный**. **Реализовать все пять правил закрытия** ([ADR-067 §3.3](../../adr/ADR-067-agent-run-background-consumer.md)) — терминальное событие может не появиться в Redis никогда, а раньше стрим закрывал сам Hermes. **С этого пути убрать** биллинг, апсерт снапшота и `mark_status`.
