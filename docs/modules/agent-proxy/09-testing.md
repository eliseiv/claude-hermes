# Agent Proxy — Testing

Стратегия — [06-testing-strategy.md](../../06-testing-strategy.md). Hermes-инстанс мокается (respx/httpx) в unit; реальный инстанс — integration/e2e.

## Unit (Hermes мокается, `HermesInstanceManager` мокается)
- `POST /v1/agent/run`:
  - policy blocked (нет подписки / 0 кредитов) → `200 {status:blocked, blockReason}`, прогон НЕ запущен, `ensure_running` не вызван.
  - allowed → `ensure_running` вызван, прокси `POST /v1/runs` с `Authorization: Bearer <api_key>`, маппинг `message→input`/`sessionId→session_id`/`model→model`, ответ `202 {runId}`.
  - инстанс недоступен / Hermes 5xx → `502` (не `200 blocked`).
  - нет `X-API-Key` / нет/невалидный `X-User-Id` → `401`.
- SSE-ретрансляция:
  - события `run.running`/`message.delta`/`tool.*`/`approval.request` пробрасываются клиенту as-is.
  - `run.completed{usage}` → `WalletService.consume(idempotency_key=runId)` ровно один раз; `amount=ceil(...)`, мин. 1.
  - `run.failed` → проброс, **без** debit.
  - повторная подписка/дубль `run.completed` того же `runId` → один debit (идемпотентность).
- `approval`/`stop` — passthrough к Hermes с корректным `runId`/Bearer.

## Integration (testcontainers Postgres + Redis; Hermes мок)
- policy ↔ wallet ↔ ledger: consume пишет `ledger_transactions(type=debit, idempotency_key=runId, meta.usage)`; баланс уменьшается один раз; `balance>=0` CHECK соблюдён.
- Источник credit-tx: agent-debit (`source=agent_run`, ключ `runId`) не конфликтует с chat-debit (`messageStepId`).

## E2E (реальный Docker + Hermes-образ, [09-e2e-testing.md](../../09-e2e-testing.md))
- `POST /v1/agent/run` нового `userId` → поднимается инстанс → `runId`; `GET .../events` стримит SSE до `run.completed`; баланс уменьшается ровно один раз (idempotency по `runId`).
- При 0 кредитов / неактивной подписке → `200 blocked` (BR-3/BR-5).
- `approval.request` → `POST .../approval` разблокирует прогон.
- `/v1/chat/*` (простой чат) продолжает работать независимо (регресс).

## Incremental billing + pause/resume ([ADR-064](../../adr/ADR-064-incremental-agent-run-billing-and-pause-resume.md), под флагом `agent_incremental_billing_enabled`)

### Unit / Integration — тарификация
- **Телескопическая сумма:** серия `usage.delta` (кумулятивы) → `Σ per-step charge == usage_to_credits(final_cumulative)` **точно** (совпадает с постфактум [ADR-047](../../adr/ADR-047-usage-based-billing-for-agent.md)); проверить, что per-step `ceil` дельт НЕ применяется (нет инфляции: сравнить с `Σ ceil(delta_i)`).
- **Per-step идемпотентность:** дубль/реплей `usage.delta` того же `step_index` → один debit (ключ `runId:step`, `ux_ledger_idempotency`).
- **Seed из ledger (reconnect):** обрыв SSE после N шагов + повторная подписка → `charged` восстановлен через `charged_for_run` (SUM по `runId OR runId:%`, `ESCAPE '\'`); шаги 1..N не списаны повторно. Кейс `run_id` с LIKE-метасимволами (`%`/`_`) → нет ложных совпадений (экранирование).
- **Финализация остатка:** `run.completed` → `remainder = usage_to_credits(final) − charged`, при `>0` debit idempotency `runId` (голый, не конфликтует с `runId:step`).
- **`charge == 0`** (concurrent chat-debit обнулил balance): debit пропущен (нет `ConflictError` от `consume(amount<=0)`), но `depleted=True` → пауза.
- **Флаг OFF:** `charged=0` → `remainder=full` на `run.completed` = постфактум [ADR-047](../../adr/ADR-047-usage-based-billing-for-agent.md); биллинговые поля `agent_runs` (`cumulative_credits_spent`/`last_billed_step`) не двигаются; `usage.delta` ретранслируется без биллинга; `resume` недоступен. **Строка `agent_runs` при этом создаётся** (lifecycle-запись, [ADR-066 §3](../../adr/ADR-066-agent-run-state-snapshot.md)) — регресс-проверка: при OFF `agent_runs[runId]` существует со `status` жизненного цикла.

### Unit / Integration — pause-at-zero + no-debt
- **Stop-at-0:** при `charge < want` → списано `min(want,balance)` (balance→0), вызван `stop(runId)` (Hermes interrupt), эмитировано терминальное `run.paused` (`reason=credits_exhausted`, промежуточный JSON из relay-буфера), `agent_runs.status='paused'`, стрим закрыт БЕЗ `run.completed`.
- **Долг НЕ вырос:** `wallets.debt == 0` после паузы; `netBalance == balance` ([ADR-063](../../adr/ADR-063-client-facing-debt-and-net-balance.md)).
- **No-debt clamp routing (MAJOR):** `consume(meta.incremental=true)` маршрутизируется в `_consume_incremental_clamp` **до** `_debit_in_savepoint`; в гонке с concurrent chat-debit (balance < amount) — списано `LEAST(amount,balance)` **без** `InsufficientCreditsError` и **без** `wallets.debt` (стрим не рвётся). Регресс: `meta` без `incremental` (chat/admin/finalization) по-прежнему идёт savepoint-путём (raise на нехватке).

### Integration — resume + concurrency
- **Resume happy-path:** paused → `POST /resume` → CAS `paused→resumed`, новый прогон (та же `session_id`), `agent_runs` chain (`continued_from_run_id==old`, old→`resumed`), `202 {runId:new, continuedFrom:old}`; свежий keyspace `new:step` (списания не пересекаются с `old:%`).
- **Concurrent-resume idempotency (CRITICAL, CAS):** два параллельных `POST /resume` того же paused `runId` → **ровно один** child-прогон Hermes (CAS пропускает одного); проигравший получает `202` с тем же child ИЛИ `409 resume_in_progress` (до фиксации child); НЕТ двух child в одной `session_id`, НЕТ двойного launch/биллинга, НЕТ orphan. Последовательный повтор после завершения (`status='resumed'`) → тот же child.
- **Гварды:** `status ∉ {paused,resumed}` → `409 run_not_resumable`; чужой/несуществующий `runId` → `404` (RBAC); баланс всё ещё 0/долг → `200 blocked` (policy-gate до CAS, статус не флипнут).
- **Reconcile на сбое:** сбой до `POST /v1/runs` после выигрыша CAS → откат `resumed→paused` (прогон снова возобновляем), `502`.
- **Hydrate:** `GET {base}/api/sessions/{session_id}/messages` → `conversation_history` подан в новый прогон; недоступна сессия → `409`/`502` ([Q-064-3](../../99-open-questions.md)).

### Миграция `0018` (real DB, testcontainers)
- `upgrade` + `downgrade` на реальной БД; `alembic heads` == 1 (single head, цепочка `0017`→`0018`); enum `agent_run_status` + таблица + 3 индекса + CHECK'и создаются/удаляются.

## Снапшот состояния прогона + `GET /v1/agent/runs/{runId}/state` ([ADR-066](../../adr/ADR-066-agent-run-state-snapshot.md))

### Unit — writer и маппинг
- **Троттлинг `message.delta`:** серия дельт внутри `AGENT_STATE_FLUSH_INTERVAL_SECONDS` → **один** апсерт; терминальные события и `approval.request` флашатся немедленно (минуя троттлинг).
- **`tool.started`/`tool.completed`** → `last_tool` обновлён, `pending_approval` очищен. **`approval.request`** → `pending_approval={tool,preview}`; `POST …/approval` (2xx) → очищен.
- **Replay-guard:** повторная подписка, где Hermes реплеит буфер с начала (короткий префикс), **не укорачивает** `result_text`; токены не убывают (`GREATEST`).
- **Truncation `preview`:** `pending_approval.preview` длиннее `AGENT_STATE_RESULT_TEXT_MAX_CHARS` обрезается тем же лимитом head-preserving (общий knob с `result_text`).
- **`clear_pending_approval` owner-scoped:** снятие approval чужим `user_id` → `rowcount=0`, `pendingApproval` не снят.
- **`assert_pending_approval` — троттлинговый флаш не воскрешает approval:** `approval.request` → `pending_approval` выставлен → `POST …/approval` (2xx) снимает его → следующий периодический флаш `message.delta` (идёт с `assert_pending_approval=false`) **не** возвращает старое значение; `/state` остаётся `running`, не откатывается в `waiting_approval`. Зеркальный кейс: апсерты с `assert=true` (`approval.request`/`tool.*`/терминальные) значение действительно меняют.
- **Терминальный статус пишется ДО биллинга и независимо от его исхода:** при `run.completed`, где `consume`/финализация поднимает ошибку (нехватка баланса, конфликт idempotency, сбой кошелька), `agent_runs.status` всё равно `completed` — «вечного `running`» не остаётся; `/state` отдаёт `completed`, retention-sweep такой прогон видит.
- **`mark_stopped` owner-scoped:** вызов с чужим `user_id` → `rowcount=0`, статус прогона не меняется (RBAC — свойство самого `UPDATE`, а не только предшествующей проверки).
- **Префиксный guard `result_text` (MAJOR):** входящий текст **длиннее** сохранённого, но **не продолжает** его (общего начала нет — сценарий no-replay, [Q-066-1](../../99-open-questions.md)) → `result_text` **не заменён**, снапшот замер на прежнем полном тексте. Парный позитив: входящий длиннее **и** продолжает сохранённый → заменён. Тест обязан падать на реализации с одной лишь проверкой длины.
- **Tenancy-гвард (MAJOR, [Q-066-2](../../99-open-questions.md)):** апсерт при конфликте `run_id` с **чужим** `user_id` → **0 строк** (чужой снапшот не перезаписан, `WHERE t.user_id = EXCLUDED.user_id`); `snapshots_repo.get(run_id, чужой user_id)` → `None`. Симметрично для `clear_pending_approval`/`mark_stopped` (уже покрыты выше).
- **Replay-guard per-column (MAJOR, регресс на row-level `WHERE`):** **внутри replay-окна** (входящий `result_text` короче сохранённого) апсерт с `approval.request` всё равно выставляет `pending_approval` → `/state` отдаёт `waiting_approval`; в том же кейсе обновляются `last_tool` и `updated_at`, а `result_text` **не укорачивается**. Тест обязан падать на реализации с `ON CONFLICT … DO UPDATE … WHERE` (гейт строки целиком).
- **Truncation:** текст длиннее `AGENT_STATE_RESULT_TEXT_MAX_CHARS` обрезан **с сохранением начала** (граничные значения: ровно потолок / потолок+1).
- **Статусы:** `run.failed` → `_mark_terminal(runId,'failed')`; `mark_stopped(run_id, user_id)` → `cancelled` **только** из `running`/`resumed` и **только** для владельца (чужой `user_id` → `rowcount=0`) (регресс: `completed`/`paused` не затираются); строки создаются при выключенном флаге биллинга.
- **Терминальные события после `stop` не затирают `cancelled` (MAJOR):** прогон помечен `cancelled` → долетевшие `run.completed`/`run.failed` из ещё открытого relay **не** меняют статус (условие `WHERE status IN ('running','resumed')`); `/state` продолжает отдавать `stopped`.
- **Pause-at-zero не проходит через `cancelled` (MAJOR):** при исчерпании баланса внутренний Hermes-interrupt ([ADR-064 §3](../../adr/ADR-064-incremental-agent-run-billing-and-pause-resume.md)) **не** вызывает `mark_stopped(...)` — наблюдаемая последовательность статусов `running → paused` без промежуточного `cancelled`; сразу после `run.paused` `/state` отдаёт `paused` (+`blockReason`), а `POST /resume` — **не** `409 run_not_resumable`.
- **Чистая функция маппинга** server→client — все семь исходов, включая `running+pending_approval → waiting_approval` и `cancelled → stopped`.

### Integration (`tests/integration/test_agent_run_state_api.py`, Postgres testcontainers; Hermes НЕ нужен)
- **401-матрица** — новый путь добавлен в общий auth-parametrize (нет `X-API-Key` / нет / невалидный `X-User-Id`).
- **404** — несуществующий `runId`; прогон другого пользователя (RBAC, **не 403**).
- **200 для каждого маппинга** — `running`, `waiting_approval`, `paused` (+`blockReason`), `completed`, `failed`, `stopped`.
- **200 без снапшота** — строка `agent_runs` есть, `agent_run_snapshots` нет → дефолты (`resultText:""`, `usage:{0,0}`, `updatedAt` из `agent_runs`).
- **Read-only инварианты (MAJOR):** `ensure_running` **не вызван**, HTTP к Hermes отсутствует, `wallets.balance`/`ledger_transactions` не изменились после запроса.
- **Retention:** терминальный прогон старше `AGENT_RUN_SNAPSHOT_TTL_DAYS` → `resultText:""`/`pendingApproval:null`, но `200` со статусом и `usage`; активный прогон того же возраста не затронут.
- **Retention идемпотентен (MAJOR):** повторный sweep по уже очищенному прогону → **`rowcount=0`** (guard `AND (result_text <> '' OR pending_approval IS NOT NULL)`), `updatedAt` **не двигается** ни на первом, ни на повторном проходе (чистка контента не является обновлением состояния). Тест обязан падать на реализации без guard'а и на реализации, трогающей `updated_at`.
- **OpenAPI-поверхность** ([ADR-059](../../adr/ADR-059-hermes-only-openapi-surface.md)) — `tests/integration/test_api_documentation.py` обновлён на новый route (тег `Agent`, security `clientApiKey`+`userId`, коды `200/401/404/429`).

### Миграция `0019` (real DB, testcontainers)
- `upgrade` + `downgrade` на реальной БД; `alembic heads` == 1 (цепочка `0018`→`0019`); таблица + 2 индекса (`ix_agent_run_snapshots_user` + **частичный** `ix_agent_run_snapshots_sweep` с предикатом `result_text <> '' OR pending_approval IS NOT NULL`; полного индекса по `updated_at` **нет** — он был бы write-amplification на самой горячей записи) + CHECK'и создаются/удаляются; enum `agent_run_status` **не изменён**; FK CASCADE от `agent_runs` и `users` работают.

### E2E (ручной, `docker-compose.e2e.hermes.yml`)
- Запустить прогон → убить SSE-потребителя → `GET /state` (статус/текст на момент обрыва) → переподключиться к `/events` → `GET /state` снова. **Ожидаемый результат ОПРЕДЕЛЁН перемером 2026-07-30:** до [ADR-067](../../adr/ADR-067-agent-run-background-consumer.md) переподписка не даёт **ничего** (поток одноразовый), текст не догоняет — это и есть корректное поведение сценария, а не дефект. **После [ADR-067](../../adr/ADR-067-agent-run-background-consumer.md)** ожидание меняется по сути: снапшот двигает consumer, поэтому `resultText` растёт **и во время обрыва**, а переподключение к `/events` даёт реплей из нашего ring (upstream при этом не трогается вовсе).

#### Семантика потока событий Hermes ([Q-066-1](../../99-open-questions.md)) — **ЗАКРЫТО перемером 2026-07-30**

**Результат (devops, после фикса парсинга, на ЗАВЕДОМО ЖИВОМ прогоне; прогоны `run_b170a402…`, `run_cfda1890…`; воспроизводится устойчиво):**

> **Поток одноразовый (single-consumption).** Историю прогона получает **первый** подписчик. **Любая повторная подписка не получает НИЧЕГО — ни реплея, ни новых событий продолжающегося прогона.** `updatedAt` при второй подписке не двигается, то есть событий не приходит вовсе, а не «приходят, но не пишутся».

| Гипотеза до перемера | Исход |
|---|---|
| `from_start` (реплей с начала при каждой подписке) | **опровергнута** |
| `new_only` (только новые события) | **опровергнута** |
| `replay-once-then-drain` (H1: реплей первому, дальше — только новые второму) | **опровергнута — реальность строже:** второй подписке не идут и новые |
| H4 (первый подписчик получает историю) | ⚠️ **НЕ упражнялась** — момент открытия подписки A относительно первых событий в артефактах не зафиксирован; если A открывалась сразу после `202`, она получила живой поток, а не историю. Проверяется отдельной пробой: подписка **заведомо позже** первых событий (выждать ≥ 10 с после `202`) |

⚠️ **Два дефекта прежней процедуры, из-за которых первый замер не считался** (устранены в этом перемере): (1) **конфаундер живости** — прогон мог завершиться до второй подписки, и «0 байт» объяснялось бы тривиально; теперь мерили на заведомо активном прогоне; (2) **негодный дискриминатор** `char_length(resultText)` — из-за дефекта парсинга `message.delta` текст был тождественно пуст, и обе ветки исходов давали «замер»; перемер выполнен **после** фикса.

**Методический вывод (переносим на будущие замеры):** дискриминатор не должен зависеть от артефакта, корректность которого сама под вопросом, а «отсутствие данных» нельзя интерпретировать, не доказав, что источник данных был жив. Вместе со вторым выводом того же семейства (симптом без кода ошибки не атрибутируется компоненту без различающего признака) — [06-testing-strategy.md §Методические выводы](../../06-testing-strategy.md).

**Что это закрывает и меняет:**
- [Q-067-1](../../99-open-questions.md) — **отрицательно**: подхват прогона (adoption) и ретрай собственной подписки **невозможны**;
- [Q-067-5](../../99-open-questions.md) — **утратил предмет** (параллельный consumer нереализуем);
- инвариант «consumer подписывается раньше клиента» ([ADR-067 §1](../../adr/ADR-067-agent-run-background-consumer.md)) — **доказанно необходим**;
- orphan-reaper — **единственный и постоянный** путь доводки; рестарт `api` под прогоном необратимо теряет биллинговый хвост → [Q-067-12](../../99-open-questions.md);
- префиксный replay-guard ([ADR-066 §6](../../adr/ADR-066-agent-run-state-snapshot.md)) — **чистый defense-in-depth**: второй потребитель не пишет ничего.

**Регресс-тест (после реализации [ADR-067](../../adr/ADR-067-agent-run-background-consumer.md), Hermes мокается):** мок отдаёт поток **только первому** подписчику, второму — пустой ответ; проверить, что (а) consumer подписывается **раньше** клиента и получает поток целиком; (б) клиентский `/events` при этом полноценно обслуживается **из broker'а**, а не из upstream; (в) при обрыве подписки consumer'а **переподключения не происходит** — прогон уходит к reaper'у.

### Фоновый consumer + broker ([ADR-067](../../adr/ADR-067-agent-run-background-consumer.md)) — что покрыть тестами

**Регресс-ядро (MAJOR, падает на сегодняшней реализации):**
- **Биллинг без единого клиентского подписчика:** прогон запущен, `/events` **никем** не открывался, мок Hermes доигрывает поток до `run.completed{usage}` → в ledger есть debit с idempotency `runId`, `agent_runs.status='completed'`, снапшот заполнен. Обе ветки флага `agent_incremental_billing_enabled`.
- **Порядок сохранён:** `_mark_terminal` вызывается **до** биллинга; при исключении из `consume` статус всё равно терминальный ([ADR-066 §3](../../adr/ADR-066-agent-run-state-snapshot.md)).
- **Клиентский `/events` ничего не пишет:** при открытом клиентском стриме дублирующих ledger-строк, апсертов снапшота и `mark_status` с этого пути нет.

**Broker (Redis — testcontainers):**
- Подписчик, подключившийся в середине прогона, получает **реплей из ring, затем live**, без дублей (дедуп по `seq`) и без пропусков на границе (`SUBSCRIBE` — **до** `LRANGE`).
- **`seq` берётся из Redis `INCR`:** после «перехвата» прогона другим воркером нумерация продолжается, а не начинается с нуля.
- **`EXPIRE` продлевается на каждом событии:** прогон длиннее `AGENT_RUN_EVENT_BUFFER_TTL_SECONDS` — ring **жив**, поздний подписчик получает реплей.
- **Двойной потолок ring:** обрезка срабатывает и по числу событий, и по `AGENT_RUN_EVENT_BUFFER_MAX_BYTES` (крупные события); байтовый счётчик `…:bytes` после серии добавлений и обрезок **равен фактической сумме длин** элементов ring'а (проверять пересчётом, а не доверием к счётчику).
- **Самое новое событие не выбрасывается никогда:** событие, одно превышающее `AGENT_RUN_EVENT_BUFFER_MAX_BYTES`, остаётся в ring'е (ring **не пуст**), а подписчик получает `run.truncated`, потому что первый доступный `seq` больше `курсор + 1`. ⚠️ Тест обязан падать на реализации, которая «честно» соблюдает потолок и выбрасывает всё.
- **Атомарность записи относительно перехвата lease:** два воркера пишут события одного `runId` конкурентно → **порядок элементов ring'а совпадает с порядком `seq`** (дедуп broker'а опирается именно на это). ⚠️ Тест обязан падать на реализации через клиентский pipeline вместо Lua: там возможно вклинивание `RPUSH` между чужим `INCR` и его `RPUSH`.
- **`AGENT_RUN_REDIS_DB` реально применён:** подключение транспорта работает в **той БД, что задана настройкой**, а не в БД из path `REDIS_URL` — проверять фактическое подключение (`CLIENT INFO`/`INFO clients` либо запись-чтение ключа в обеих БД), **а не значение конфига**. ⚠️ Регресс на найденную ловушку: `redis.from_url(url, db=N)` молча игнорирует `db` при наличии path в URL, и валидатор конфигурации остаётся зелёным.
- **Backpressure:** переполнение `AGENT_RUN_SUBSCRIBER_QUEUE_MAX` отключает **подписчика**; consumer продолжает, биллинг и снапшот доходят до конца.
- ⛔ **Ось D, режим D2 — звено ЗАВИСЛО (не умерло):** `await` в цикле доставки без предельного срока даёт **тот же** наблюдаемый исход (открытый пустой стрим) при **живой** задаче-читателе, поэтому правило 6 по своему условию **не срабатывает**. Тест: периодическая проверка на отдающей стороне (`_is_terminal` — запрос к `agent_runs`; `lease_alive` — Redis) блокируется ⇒ запрос обязан **завершиться** (ошибка/закрытый стрим) за предельный срок, а не висеть. ⚠️ **Мутация: снять предельный срок ⇒ тест обязан краснеть ЗАВИСАНИЕМ.** ⛔ **Признаковые меры здесь бессильны по построению** — признак правила 6 (`done()`/`Event`) снимается **в цикле отдачи**, а он и заблокирован; поэтому альтернативная приёмка — периодические проверки **вынесены** с пути доставки (тогда блокировка проверки не останавливает запись клиенту). Сегодня предела нет: `DB_POOL_TIMEOUT` ограничивает ожидание **из пула**, а `statement_timeout`/`lock_timeout` не заданы нигде ([Q-067-20](../../99-open-questions.md)) — это тот же класс, что [TD-040](../../100-known-tech-debt.md) (`await` без предельного срока, цена — зависание ≥90 с).
- ⛔ **Путь завершения не проходит через полную очередь:** при `QueueFull` **и** при смерти читателя отключение исполняется **вне** очереди (отмена писателя либо `Event`, ожидаемый совместно с `queue.get()`). ⚠️ **Мутация: сигнализировать завершение in-band sentinel'ом без зарезервированного слота ⇒ тест обязан краснеть зависанием** — положить его в полную очередь невозможно, то есть сигнал недоступен ровно в том отказе, для которого введён.
- ⛔ **`QueueFull` не срабатывает на дублях перекрытия (по построению):** клиент, **полностью** получивший реплей (`600` блоков и более), при дренаже канальных копий тех же событий **не отключается** — классификация выполняется **до** очереди, и дубли в неё не попадают. ⚠️ **Регресс критичен именно после [TD-047](../../100-known-tech-debt.md):** подписка встаёт до `LRANGE`, поэтому копии **всех** реплеенных событий приходят всегда, и при ring `5000` против глубины `500` реализация «кладём всё пришедшее» отключала бы клиента на **каждом** реконнекте к полному ring'у. Провенанс входа: наблюдение qa на прогоне (отдельным тестом не фиксировалось) — этот пункт и есть его фиксация.
- ⛔ **Реплей выполняет ЧИТАТЕЛЬ (§3.2.2, вариант «а») — ассерт на устройство, а не только на исход:** `SUBSCRIBE` → `LRANGE` → классификация происходят **в одной задаче**, поэтому baseline реплея (`delivered`, `replay_min_seq`) готов **до** обработки первого канального сообщения. ⚠️ **Тест обязан падать на реализации, где реплей остаётся у вызывающей стороны:** там читатель классифицирует с `delivered = 0`, и канальные копии **всего** ring'а признаются причитающимися ⇒ клиент получает перекрытие **вторым экземпляром** (при полном ring'е — `5000` дублей). Ассерт: после реконнекта к полному ring'у клиент получает каждое событие **ровно один раз**. ⛔ **Теста на «подтверждение подписки» БОЛЬШЕ НЕТ** — мера снята вместе с кросс-задачным окном; от [TD-047](../../100-known-tech-debt.md) остаётся проверка **порядка** внутри читателя и запрет **ленивой** подписки (фактический `SUBSCRIBE` выдан до `LRANGE`).
- ⛔ **Периодические проверки — в СУПЕРВИЗОРЕ, не в читателе:** ассерт «блокировка `_is_terminal`/`lease_alive` не останавливает ни чтение канала, ни запись клиенту» — события продолжают доходить. ⚠️ **Мутация: перенести проверки в читателя ⇒ тест обязан краснеть зависанием** (заблокированный читатель жив, правило 6 молчит, канал не читается, писатель висит на пустой очереди — молчащий стрим при трёх формально живых задачах). Это прямо запрещённый вариант, и он выглядит самым дешёвым.
- ⛔ **Штатное и аварийное завершение разведены (§3.2.2):** **(1) штатный** — терминальное событие в очереди, читатель закончился ⇒ писатель **осушает очередь до конца** и клиент получает `run.completed`, и только потом EOF; **(2) аварийный** (`QueueFull` / смерть читателя / D2-таймаут / супервизор) ⇒ очередь бросается немедленно. ⚠️ **Мутация: завершать штатный путь тем же аварийным `Event`** ⇒ тест (1) обязан краснеть — при одновременной готовности `FIRST_COMPLETED` вправе выбрать `Event`, и клиент получит EOF **без** `run.completed`, то есть правило закрытия 1 деградирует в «добирай из `/state`». ⚠️ Парный ассерт: sentinel штатного конца проходит **при полной** очереди (зарезервированный слот), а не блокируется.
- ⛔ **Зарезервированный слот — ассерт на МЕХАНИЗМ:** очередь заполнена до предела, читатель кладёт sentinel штатного конца ⇒ он **помещается**, и клиент получает терминальное событие. ⚠️ **Мутация: сравнивать с `maxsize` вместо `AGENT_RUN_SUBSCRIBER_QUEUE_MAX` (то есть разрешить обычным элементам занять последний слот) ⇒ тест обязан краснеть ПОТЕРЕЙ терминального события** — читатель уйдёт на аварийный путь и выбросит уже лежащее в очереди `run.completed`. Резерв обеспечивается **правилом** «обычные элементы только пока `qsize() < AGENT_RUN_SUBSCRIBER_QUEUE_MAX`», а не свойством `maxsize = N + 1`.
- ⛔ **Признак штатного конца — ФЛАГ, выставляемый на КАЖДОМ пути штатного возврата читателя ДО возврата (§3.2.2):** писатель решает по флагу, а не по содержимому очереди. **Два ассерта:** (1) флаг выставлен ⇒ осушение до sentinel'а, клиент получает `run.completed`; (2) флага нет (авария: `QueueFull` при мёртвом читателе, D2-срок) ⇒ очередь бросается **немедленно**, писатель **не блокируется** на пустой очереди в ожидании sentinel'а, которого не будет. ⚠️ **Мутации:** «писатель всегда осушает до sentinel'а» ⇒ тест (2) краснеет **зависанием**; «различать пути только по аварийному сигналу» ⇒ краснеет **шесть** тестов (замерено) — в этом и вся несущая роль флага. ⛔ **Теста на порядок «флаг раньше sentinel'а» НЕТ, и он не пишется:** мутация «sentinel раньше флага» (с уступкой планировщику в окне) **не роняет ничего** — писатель на присутствие sentinel'а **не решает**, а получает его, причём **последним**, поэтому к моменту извлечения всё предшествующее уже отдано; ассерт на порядок строк был бы ассертом на текст, а не на поведение. **Несущее здесь другое:** читатель, вернувшийся **без флага** при непустой очереди, отправляет писателя на аварийную ветвь (`reader.done()`) — и причитающееся выбрасывается; проверяется теми же шестью тестами. ⚠️ `asyncio.Queue` не даёт `peek`, поэтому «посмотреть, лежит ли sentinel» — нереализуемое поведение.
- ⛔ **Teardown ВОЗВРАЩАЕТСЯ, а не бросает (свойство P1 строки «Разрыв конвейера»):** отключение клиента ⇒ `aclose()` **возвращается**, а не поднимает `BaseExceptionGroup`. ⚠️ **Найдено прогоном, путь штатный** (каждое отключение): `GeneratorExit` есть `BaseException`, и `TaskGroup.__aexit__` перебрасывает его **завёрнутым**; воспроизводится в 20 строках без кода проекта, тест **сегодня красный**. **Три парных ассерта на свойства, которые давала группа и обязана дать заменяющая конструкция:** **(P2)** отмена звеньев завершается за ограниченное время (статический гвард на запрещённые конструкции); **(P3)** исключение в любом звене **отменяет** остальные — нет осиротевших задач (обеспечено явно: обе задачи в наборе ожидания писателя, упавшая отдаёт исключение в лог, `finally` отменяет sibling'а). ⛔ **Намеренное исключение из P3, для которого нужен ОТДЕЛЬНЫЙ позитивный тест:** исключение **супервизора** во время штатного осушения **игнорируется** — клиент обязан получить всё, включая терминальное событие. Мутация «обрывать осушение на любом исключении» краснеет потерей `run.completed`; ⚠️ без этого теста следующий ревьюер прочтёт исключение как пробел и «починит» его; **(P4)** нормальное завершение одного звена **НЕ отменяет** остальные — читатель, закончивший штатно, не обрывает осушение (мутация «завершение любого звена отменяет группу» ⇒ краснеет потерей терминального события).
- ⛔ **Переход в live — по гистерезису, а не на границе фаз:** реконнект к **полному** ring'у (5000 блоков при пороге 500) ⇒ после конца реплея читатель остаётся в дисциплине реплея, пока очередь не опустится до **`AGENT_RUN_SUBSCRIBER_QUEUE_MAX / 2`** (250), и **только потом** переходит к `put_nowait`. Ожидание: клиент, честно осушивший реплей, **не отключается**. ⚠️ **Мутация: переключать фазу сразу по концу реплея ⇒ тест краснеет отключением** — очередь на границе полна **по построению** (реплей кладёт до предела, ожидая места; канальные сообщения копились всю фазу), поэтому первая live-постановка ушла бы на аварийный путь. Парный ассерт: клиент, так и не опустивший очередь до половины, отключается **по времени** (`AGENT_RUN_SUBSCRIBER_DRAIN_SECONDS`), а не по глубине. ⚠️ Второй парный негатив — на **дребезг**: клиент, колеблющийся вокруг предела, не отключается на каждом всплеске.
- ⛔ **Срок ограничивает ОДНО ОЖИДАНИЕ, отсчёт от последнего успешного прогресса** (поправка по прогону): клиент, берущий **медленно, но исправно** (`0.1 с/блок`, `41` блок = `4.1 с` при бюджете `3 с`), обязан получить **всё**, включая терминальный блок. ⚠️ **Мутация: считать срок на всю фазу по стенным часам ⇒ тест краснеет потерей РОВНО ПОСЛЕДНЕГО, терминального блока** (второй тест — `76` из `100`). Парный ассерт: клиент, **переставший брать вообще**, отключается по сроку. ⚠️ Ассерт «суммарное удержание ≤ `2 ×` значения» ставить **нельзя**: это граница только для случая «медленный реплей, затем медленное осушение», а клиент, возобновляющий чтение перед каждым сроком, законно удерживается дольше — потолок даёт `AGENT_RUN_MAX_DURATION_SECONDS`.
- ⛔ **Отступ супервизора — ПРАВИЛО КОРРЕКТНОСТИ, и его признак — ПРОГРЕСС ПИСАТЕЛЯ, а не знание читателя.** **Три обязательных теста:** **(1) замеренный случай:** прогон **терминальный на открытии**, реплей `41` блок при клиенте `0.1 с/блок` (`4.1 с`) и тике супервизора `2 с` ⇒ клиент получает **все** блоки и терминальное событие (без отступа замеры дали `40` из `41`, при строгом аварийном пути `20` из `41`); **(2) ⛔ прогон, ставший терминальным ВО ВРЕМЯ выдачи:** **не** терминален на открытии, терминального события в ring'е нет, ring `41` блок, клиент `0.1 с/блок`, consumer завершает прогон на ~`2`-й секунде выдачи, тик `2 с` ⇒ ассерт «клиент получил все `41` блок **и** терминальное событие». ⚠️ **Предикат отступа — КОНЪЮНКЦИЯ из двух условий, и у каждого свой тест; ни одно не снимать как избыточное:** **(а) `not queue.empty()`** и **(б) последняя отданная порция свежее `AGENT_RUN_SUBSCRIBER_DRAIN_SECONDS`**. **Мутация «снять (а)» ⇒ краснеет `test_rule_5_idle_with_no_lease_closes`** — замер: **таймаут 15 с** при бюджете `120 с` и idle `1 с`, то есть правило 5 не срабатывало **вовсе** (до правки стрим закрывался за **~2 с**); причина — после последней порции завершённой выдачи супервизор оставался заглушённым **весь бюджет**, хотя отдавать нечего. **Мутация «снять (б)» ⇒ краснеет зависанием** (сцена ниже). ⚠️ **Отступ обязан быть ПРОПУСКОМ ТИКА, а не выходом из цикла:** мутация «выйти из цикла супервизора» краснеет тем же зависанием, потому что правила 4/5 выключаются навсегда.
- ⛔ **СЦЕНА для конъюнкта (б) — иначе мутация ИНЕРТНА (замерено backend: во всех нынешних тестах пауза клиента одноразовая и короче бюджета, поэтому снятие (б) ничего не роняет).** Требуемое состояние: **очередь НЕПУСТА** (иначе сработает (а) и тест ничего не скажет о (б)) **и** клиент молчит **дольше** бюджета. Рецепт: `AGENT_RUN_SUBSCRIBER_DRAIN_SECONDS` в тесте мал (например `0.2 с`), клиент забирает часть блоков и **замолкает навсегда**, при этом в очереди остаются блоки, а правило 4 или 5 истинно ⇒ стрим обязан **закрыться**. ⛔ Пауза короче бюджета либо пустая очередь делают мутацию неразличимой — это и есть та ошибка, которая уже трижды повторялась.
- ⛔ **СЦЕНА для резерва слота под sentinel + ИСПРАВЛЕННЫЙ способ покраснения.** Требуемое состояние: `qsize()` **ровно на пороге** `AGENT_RUN_SUBSCRIBER_QUEUE_MAX` в момент, когда читатель ставит sentinel (инструментировать и **проверить** это в тесте: замер qa — `qsize = 11`, `maxsize = 11`). Рецепт: порог в тесте мал (например `3`), клиент **не читает вовсе**, ring содержит `≥ 4` блока и заканчивается **терминальным** событием ⇒ читатель заполняет очередь до порога и ставит sentinel в **резерв**; затем клиент начинает читать. ⛔ **Ассерт — на ЗАДЕРЖКУ ЗАКРЫТИЯ, а НЕ на потерю данных.** Мутация «сравнивать с `maxsize` вместо порога» даёт `QueueFull`, читатель **падает** (залогированный отказ), но клиент **всё равно получает все блоки, включая `run.completed`** — замер qa: `12` из `12`; закрытие при этом просрочено ровно на `DRAIN_SECONDS` (`5.1 с` против `2.0 с` паузы), потому что осушение кончается **по бюджету**, а не по sentinel'у. ⚠️ **Прежнее ожидание «краснеет потерей терминального события» было НЕВЕРНЫМ** — именно поэтому мутация выглядела инертной: backend искал потерю, которой там нет. **Причина — взаимодействие требований:** к моменту падающей постановки флаг штатного конца уже взведён, поэтому писатель идёт путём осушения ([ADR-067 §3.2.2](../../adr/ADR-067-agent-run-background-consumer.md)). ⛔ **Мутации «снять резерв» и «поменять порядок флаг/sentinel» МАСКИРУЮТ друг друга — снимать только по одной:** при обратном порядке та же поломка даёт **потерю** терминального события (писатель уходит на аварийную ветвь по `reader.done()` до взведения флага).
- ⛔ **СЦЕНА для конъюнкта `not queue.empty()` — сегодня он НЕ ЗАКРЕПЛЁН тестом.** Требуемое состояние: очередь **ПУСТА**, прогон **не** терминален, lease **снят**, клиент **активно читает** и уже всё вычитал. Ожидание: правило 5 закрывает стрим за `AGENT_RUN_DOWNSTREAM_IDLE_TIMEOUT_SECONDS` (**~2 с**), а **не** за `AGENT_RUN_SUBSCRIBER_DRAIN_SECONDS` (в проде `120 с`). ⛔ **Мутация «снять конъюнкт `not queue.empty()`» обязана краснеть ЗАДЕРЖКОЙ ЗАКРЫТИЯ** (стрим живёт весь бюджет вместо idle-таймаута), а **не** потерей данных — как и у резерва. ⚠️ Пустая очередь здесь **обязательна**: при непустой сработает конъюнкт свежести, и тест ничего не скажет об этом конъюнкте (см. взаимную маскировку конъюнктов в ADR).
- ⚠️ **Мутация: оставить отступ по перечню «что читатель узнал» (терминален при открытии / терминальное событие в реплее / положено в live) ⇒ тест (2) краснеет потерей доставки** — знание возникает **вне** читателя (терминальность пишет consumer в БД), и перечислить его состояния нельзя по построению; **(3) ⛔ ЗАВЕРШАЕМОСТЬ:** писатель перестал отдавать (клиент замолчал) дольше `AGENT_RUN_SUBSCRIBER_DRAIN_SECONDS` ⇒ супервизор **возвращается** к правилам 4/5 и стрим закрывается. ⚠️ **Мутация: бессрочный отступ (отступ без обоих конъюнктов — например по факту «конец известен») ⇒ тест (3) краснеет ЗАВИСАНИЕМ** — правила 4/5 выключены навсегда, а вместе с правилом 4 перестаёт наблюдаться и `AGENT_RUN_MAX_DURATION_SECONDS`; ⛔ обоснование «стрим всё равно закроет читатель» **ложно**: `get_message` по таймауту возвращает `None`, и читатель живёт, пока жив канал. ⚠️ **Четвёртый ассерт:** признак перепроверяется **после** probe (мутация «проверять только до probe» краснеет флейком). ⚠️ Форма — **состояние**, не отмена задачи: мутация «отменять супервизора и ждать его завершения» вводит межзадачную точку ожидания (D2).
- ⛔ **Бюджет — ДВА срока по фазам от одного значения:** фаза реплея (у читателя) и штатное осушение (у писателя) имеют **каждый свой** отсчёт. ⚠️ **Мутация: общий счётчик на обе фазы ⇒ тест краснеет потерей терминального события** — медленный реплей израсходовал бы весь бюджет, и осушению остался бы ноль, то есть приоритет штатного пути обнулился бы истечением срока. ⚠️ **Ассерт на верхнюю границу ставится ТОЛЬКО с условием в самом ассерте:** «клиент, **переставший брать** в реплее и затем **переставший брать** в осушении, удерживается не дольше `2 ×` значения». ⛔ **Общий ассерт «суммарное удержание ≤ `2 ×`» ЗАПРЕЩЁН** — клиент, возобновляющий чтение перед каждым сроком, законно удерживается дольше, и такой тест объявил бы корректную реализацию дефектной (см. пункт про отсчёт от прогресса выше — противоречие между этими двумя пунктами устранено здесь).
- ⛔ **Супервизор не обрывает штатное осушение:** прогон терминален (правило 4 истинно) **и** lease уже снят (правило 5 истинно), sentinel положен, осушение длится **дольше тика супервизора** (30 с) ⇒ клиент всё равно получает **всё**, включая `run.completed`. ⚠️ **Мутации и роли механизмов — ДВА несущих, один необязательный:** (1) убрать **флаг** «штатный конец» ⇒ краснеет **потерей терминального события** (писатель остаётся без признака); (2) убрать **отступ супервизора целиком** ⇒ краснеет **потерей доставки у завершённого прогона** (супервизор выносит вердикт, пока читатель ещё складывает блоки); (3) убрать **отмену супервизора**, оставив первые два ⇒ остаётся **зелёным**: отмена — оптимизация (сокращает окно, убирает лишние обращения к БД). ⚠️ Отмена, если выполняется, — **без `await`** на отменённой задаче, иначе это межзадачная точка ожидания (D2).
- ⛔ **Предельный срок штатного осушения (`AGENT_RUN_SUBSCRIBER_DRAIN_SECONDS`):** клиент, перестающий читать в момент осушения, не держит стрим бесконечно — запрос завершается по сроку. ⚠️ Здесь **нельзя** опираться на `QueueFull`: читатель уже закончился, очередь никто не наполняет, переполнение невозможно. Мутация «убрать срок» ⇒ краснеет **зависанием**.
- ⛔ **Реплей ПРОТЕКАЕТ через очередь (арифметика `5000` против `500`):** реконнект к **полному** ring'у (`AGENT_RUN_EVENT_BUFFER_MAX` = 5000 при глубине 500) ⇒ клиент получает **все** блоки, отключения **не происходит**. ⚠️ **Мутация: `put_nowait` в фазе реплея (как в live) ⇒ тест краснеет отключением** — то самое «отключение на каждом переподключении», только теперь на блоках, реально причитающихся клиенту. Парный тест: **медленный** клиент на реплее отключается **по времени** (`AGENT_RUN_SUBSCRIBER_DRAIN_SECONDS`), а не по глубине — и лог называет именно эту причину.
- ⛔ **Инвариант устройства: между `SUBSCRIBE` и концом реплея читатель НЕ читает канал.** Ассерт: сообщение, опубликованное **во время** `LRANGE`, обрабатывается **после** реплея, с уже установленным baseline (`delivered`/`replay_min_seq` от реплея). ⚠️ **Мутация «подчитаем канал, пока идёт `LRANGE`» ⇒ тест краснеет двойной доставкой перекрытия** (классификация с нулевым baseline). Это ассерт на **устройство**: свойство «baseline готов раньше канальных сообщений» держится на том, что `get_message` в этом окне не вызывается ни разу.
- ⛔ **Ось D — РАЗРЫВ конвейера отменяем за ограниченное время ([ADR-067 §3.2.1](../../adr/ADR-067-agent-run-background-consumer.md), D1 требование 2):** клиент отключается посреди потока ⇒ запрос завершается **сразу**, `aclose()` не висит, задачи не утекают. ⚠️ **Механика:** `GeneratorExit` приходит в `yield` внутри `async with TaskGroup`, `finally` отменяет детей **без ожидания**, но `TaskGroup.__aexit__` их **дожидается** — этот `await` ничем не ограничен, и его мгновенность держится **только** на отменяемости детей. **Мутация (обязательна, иначе инвариант не проверен): добавить в читателя или супервизора `except CancelledError` без `raise` либо обернуть их работу в `asyncio.shield` ⇒ тест обязан краснеть ЗАВИСАНИЕМ `aclose()`**, а не ошибкой. ⚠️ Вред здесь **наш, а не клиентский** (клиент уже ушёл): утечка задачи обработчика, при масштабе — исчерпание воркеров; поэтому ассерт ставится на **завершение запроса и отсутствие живых задач**, а не на то, что видит клиент. Статический парный контроль: в задачах горячего пути нет `shield`, `except CancelledError` без `raise`, `except BaseException`, bare `except:`.
- ⛔ **Ось D, режим D1 — звено УМЕРЛО ([ADR-067 §3.2.1](../../adr/ADR-067-agent-run-background-consumer.md), правило закрытия 6):** смерть задачи-читателя канала (исключение / отмена) обязана **закрыть клиентский стрим**, а не оставить его открытым и пустым. ⚠️ **Ни один член A/B/C здесь не срабатывает по построению** — событий не приходит вовсе, сравнивать нечего, а правила закрытия 4 и 5 требуют терминального статуса и мёртвого lease, которых нет. **Три ассерта:** **(1)** исключение в читателе ⇒ стрим завершён (клиент видит конец потока, переподключается, получает реплей); **(2)** отмена запроса ⇒ читатель отменён в `finally` вместе с подпиской (нет утечки задач и подписок); **(3)** ссылка на задачу удерживается на всё время запроса — fire-and-forget запрещён. ⛔ **Мутация:** убрать sentinel/`done()`-проверку ⇒ тест (1) обязан краснеть **зависанием**, а не ошибкой; если он остаётся зелёным, ассерт проверяет не то.
- ⛔ **Порядок `SUBSCRIBE` → `LRANGE` внутри читателя ([TD-047](../../100-known-tech-debt.md), связка с [TD-048](../../100-known-tech-debt.md)):** событие, опубликованное между подпиской и концом реплея, **доходит** до клиента. ⚠️ Проверяется как **порядок операций одной задачи** — механизма «подтверждение готовности» больше нет (§3.2.2, вариант «а»), поэтому тест на кросс-задачное окно не нужен; вместо него обязателен негатив на **ленивую** подписку: фактический `SUBSCRIBE` выдан **до** `LRANGE`, а не отложен до первого `get_message`.
- **`delivered` продвигается при каждой отдаче** — отдельный ассерт на ветви, где это было пропущено в спецификации: **усыновление** (шаг 1) и **штатная отдача** (шаг 6). ⚠️ **Мутация «не двигать `delivered` в этих ветвях»** обязана краснеть **двумя** тестами: дубли перекрытия начинают переотдаваться **и** мера C2 не срабатывает **ни разу** (её условие `delivered > 0` не становится истинным).
- ⛔ **РАЗЛИЧИТЕЛЬ backpressure — два теста-близнеца на ОДНОМ потоке** ([ADR-067 §3.2.2](../../adr/ADR-067-agent-run-background-consumer.md), [TD-048](../../100-known-tech-debt.md)). Поток `600` событий при пороге `500`, различаются **только** скоростью потребителя: **(а) быстрый** потребитель обязан **дожить до конца** и получить все `600`; **(б) медленный** (искусственная задержка на чтении) обязан быть **отключён**. ⚠️ **Сегодня поведение ОБРАТНОЕ**, потому что `_iter_messages` считает сообщения **между двумя пустыми опросами канала** — размер всплеска, в котором скорость клиента не участвует вовсе: быстрый отключается на непрерывной выдаче, медленный не отключается никогда. **Порядок фиксации:** первым коммитом близнецы пишутся как **фиксация текущего поведения** (быстрый падает, медленный проходит), вторым — после [TD-048](../../100-known-tech-debt.md) — переворачиваются в требование. ⛔ **Мутация, обязанная краснеть:** возврат счётчика «сообщений между пустыми опросами» вместо глубины явной очереди. Локально, без прода.
- **Правила закрытия downstream ([ADR-067 §3.3](../../adr/ADR-067-agent-run-background-consumer.md)) — по одному тесту на условие:** терминальное событие; терминальный `agent_runs.status` при открытии; нет lease + пустой ring; статус стал терминальным во время стрима; idle-timeout без lease. **Ни в одном случае клиент не висит бесконечно.**
- **Best-effort ring:** недоступность Redis при записи не роняет consumer — биллинг и снапшот доходят.

**Владение и живучесть:**
- **Lease:** два воркера на один `runId` → upstream-подписку держит один; при принудительном истечении lease и появлении второго consumer'а **двойного списания нет**.

**Трёхзначный lease и недоступность Redis ([ADR-067 §4.1](../../adr/ADR-067-agent-run-background-consumer.md), ревизия 2026-07-31) — тесты УТВЕРЖДАЮТ выбранное поведение.** Redis мокается (`RedisError` / `SET NX` без установки ключа); реальный Redis не нужен.
- **`RedisError` на взятии lease ⇒ прогон ВЕДЁТСЯ.** Ожидание: upstream-подписка **открыта** (в моке Hermes зафиксирован запрос к `…/v1/runs/{runId}/events`), строка снапшота создана, поток обработан, на `run.completed{usage}` есть debit с idempotency `runId` и `agent_runs.status='completed'` — **как при живом Redis**. ⚠️ Тест обязан падать на сегодняшней реализации, где `upstream.requests == []`.
- **Чужой существующий lease ⇒ прогон НЕ ведётся.** `SET NX` **без ошибки** не установил ключ ⇒ upstream-запроса **нет вовсе**, handshake помечен неуспешным. ⚠️ Парный к предыдущему: он и отделяет «уходим по свидетельству» от «уходим по незнанию». Один тест без другого доказывает не то поведение.
- **`RedisError` на продлении не убивает прогон:** рабочая задача **не отменяется**, прогон доходит до терминального события. ⚠️ Тест обязан падать на реализации, где `RedisError` отображён в `LOST`; без него правка взятия lease бесполезна — прогон умирал бы на первом тике продления, уже потребив одноразовый поток.
- **Чужой владелец на продлении убивает прогон** (`LOST` при чужом uuid) — рабочая задача отменяется, audit `agent_run_consumer_shutdown`. Регресс на «расширение» послабления с `RedisError` на все исходы.
- **Восстановление Redis в середине прогона:** после сбоя на старте ближайший тик продления даёт `REACQUIRED`, ключ `…:lease` принадлежит **нам**, `epoch` заменён на новое поколение (события далее публикуются под ним).
- **Guard инертной подписки не зависит от Redis:** при недоступном Redis подписка, не получившая **ни одного байта**, снимается за `AGENT_RUN_FIRST_BYTE_STALL_SECONDS`. ⚠️ Регресс на предположение, что guard опирается на Redis-ключ `…:bytes`: он опирается на `bytes_read` beacon'а (колбэк `on_bytes` на сырых чанках), а `…:bytes` — счётчик размера ring'а, другой объект.
- **§6.4 покрывает всю жизнь consumer'а:** отказ `prepare_consumer_snapshot` (`SQLAlchemyError`) ⇒ lease **снят**, handshake помечен неуспешным (вызывающий не ждёт весь `AGENT_RUN_HANDSHAKE_TIMEOUT_SECONDS`), audit записан. ⚠️ Тест обязан падать на реализации, где вызов стоит **вне** `try/finally` ([TD-043](../../100-known-tech-debt.md)).
- **Heartbeat в `agent_run_snapshots.consumer_heartbeat_at`** идёт даже когда событий нет (длинный tool-call) и при флаге OFF; строка снапшота создаётся **при старте** consumer'а, а не лениво.
- **Потолок длительности** (`AGENT_RUN_MAX_DURATION_SECONDS`): consumer самозавершается, снимает lease и heartbeat, пишет audit и **не выставляет терминальный статус сам**; прогон затем добивает reaper.
- **Обрыв своей upstream-подписки:** §6.1 без переподключения; **ретрая нет** ([ADR-067 §6.2](../../adr/ADR-067-agent-run-background-consumer.md)).

**Orphan-reaper:**
- Кандидат = нет lease **и** протух heartbeat (`COALESCE(snapshot.consumer_heartbeat_at, agent_runs.created_at)`) **и** `INFO server → uptime_in_seconds >= AGENT_RUN_ORPHAN_REDIS_GRACE_SECONDS` → best-effort `consume` (idempotency `runId`) + `status='failed'` + audit; **повторный тик идемпотентен**.
- **Fail-closed по `INFO`:** ошибка/недоступность `INFO server` → свип **не выполняется** (ни одной финализации).
- **Fail-fast конфигурации:** `AGENT_RUN_MAX_DURATION_SECONDS <= 0` → приложение **не стартует** (валидация в `config.py`). Значение бесшумно снимает единственную гарантию верхней границы, поэтому падение на старте — требуемое поведение, а не грубость.
- **Перезапуск Redis не вызывает массовой финализации:** все lease исчезли, но живые consumer'ы обновляют heartbeat → кандидатов нет. Тест обязан падать на реализации, где условие только «нет lease».
- **`AGENT_RUN_ORPHAN_MAX_PER_TICK`** ограничивает число финализаций за тик.
- **Недоступность Redis** → свип не выполняется вовсе.
- **Списание — за вычетом уже списанного** ([ADR-067 §5](../../adr/ADR-067-agent-run-background-consumer.md) шаг 1): при `AGENT_INCREMENTAL_BILLING_ENABLED=true` прогон с пошаговыми debit'ами по ключам `runId:step` финализируется на **остаток** `usage_to_credits(...) − charged_for_run(runId)`, а не на полную сумму. ⚠️ Тест обязан падать на сегодняшней реализации: ключ `runId` свободен, идемпотентность не срабатывает, и прогон списывается **дважды целиком** ([TD-042](../../100-known-tech-debt.md)).
- **Три основания списания различимы** ([ADR-067 §5.2](../../adr/ADR-067-agent-run-background-consumer.md)): строки снапшота нет → `billingBasis="no_snapshot"`; строка есть с нулями → `"zero_usage"`; строка с ненулевым кумулятивом → `"snapshot"`. Значение попадает и в audit-payload `agent_run_orphan_finalized`, и в метку счётчика `agent_run_orphan_finalized_total{basis}`. ⚠️ Тест обязан падать на реализации с `COALESCE(...,0)` без различения: там первые два случая неотличимы, и «бесплатный прогон, которого никто не потреблял» выглядит как штатный ноль.
- **Статус финализируется в обоих нулевых случаях:** `failed` ставится и при `no_snapshot` — верхняя граница §6.5 не обменивается на точность ярлыка (парный негатив: прогон не остаётся `running`).

**RBAC на `runId`-эндпоинтах (регресс на исчезнувшую гарантию):**
- **`GET …/events` с ЧУЖИМ `runId` → `404`**, не `403` и не поток чужих событий. ⚠️ Тест обязан падать на реализации broker'а без явной проверки владения: он читает Redis по `run_id` из пути, и прежняя гарантия «чужой недостижим по построению» там **не действует**.
- **То же для `/state`, `/resume`, `/approval`, `/stop`** — проверка единообразна по ресурсу, а не по эндпоинту ([06-rbac.md](06-rbac.md)). Несуществующий и чужой `runId` дают **одинаковый** ответ (не раскрываем существование).
- **Проверка — первым шагом:** для `/approval`/`/stop` чужой `runId` **не доходит** до `ensure_running` и passthrough (иначе запрос уходил бы в инстанс субъекта и полагался бы на то, что тот его не знает).
- **`404` на `/events` реально достижим:** проверка стоит в **обработчике**, до создания `StreamingResponse`. Проверять на **реальном ASGI** (с `BaseHTTPMiddleware`), а не на упрощённом стенде: прежняя форма даёт `RuntimeError`, правильная — `404`, **и соединение после него живо**. ⚠️ Тест обязан падать на реализации с проверкой только внутри генератора — там `http.response.start` уже отправлен и статус невыразим.
- **Защита в глубину сохранена:** прямой вызов генератора (минуя обработчик) с чужим `runId` тоже обязан упасть — гарантия не должна зависеть от того, что вызывающий помнит про предварительную проверку.
- **Инвариант неразличимости — проверять формой запроса, а не порядком кодов:** при **фиксированной** форме ответ одинаков для своего / чужого / несуществующего `runId`. Тело валидно → `404` для чужого и несуществующего; тело **невалидно** → `422` для **всех трёх**. ⚠️ Тест **не** должен требовать «`404` раньше `422`»: `422` от `runId` не зависит и утечкой не является (как `401`/`413`/`429`).

**Курсор реконнекта, поколение ring'а и усечение ([ADR-067 §3.2/§3.4](../../adr/ADR-067-agent-run-background-consumer.md)):**
- Реконнект **с** `Last-Event-ID: <epoch>-<seq>` → приходят только события с `seq >` курсора **того же поколения**, дублей нет.
- **Смена поколения (CRITICAL-регресс):** прогон идёт, клиент держит курсор → **`FLUSHDB` / перезапуск Redis** → consumer жив, lease восстановлен, `seq` начинает с 1 → клиент переподключается со **старым** курсором. Ожидание: `epoch` не совпал → курсор трактуется как пустой → клиент получает **`run.truncated` + полный реплей нового поколения + live**. ⚠️ **Тест обязан падать на реализации с голым `seq`**, где клиент получил бы навсегда открытый молчащий стрим (события с `seq` 1,2,3… отбрасывались бы как `<= 500`, а правила закрытия §3.3 не сработали бы из-за живого lease).
- **Смена поколения ПОД ОТКРЫТЫМ соединением (CRITICAL-регресс, отдельно от реконнекта):** клиент **уже подключён и получает поток** → `FLUSHDB` / перезапуск Redis → pub/sub broker'а переустанавливается, consumer **жив** (lease восстановлен) и публикует с новым `epoch`, `seq` 1,2,3… Ожидание: broker обнаруживает несовпадение `epoch` **на самом событии**, сбрасывает внутренний курсор в `0`, отдаёт **`run.truncated`** и продолжает поток нового поколения. ⚠️ **Тест обязан падать на реализации, где `epoch` сверяется только при открытии стрима:** там все живые события отбрасывались бы как `seq <= 500`, правила закрытия §3.3 не сработали бы (lease живой), и клиент получил бы **молчащий стрим до конца прогона**. Проверить точки сверки: на событии и в периодической сверке §3.3 п. 4. ⚠️ **Третья точка («при восстановлении pub/sub») сегодня удовлетворена ОТСУТСТВИЕМ реконнекта** — `RedisError` на чтении канала закрывает клиентский стрим, и клиент переподключается с полной проверкой ([ADR-067 §3.3.1](../../adr/ADR-067-agent-run-background-consumer.md) п. 2). Поэтому тест на неё формулируется **негативно**: broker **не восстанавливает** подписку молча; если реконнект появится — вместе с ним обязана прийти сверка `epoch`.
- **CRITICAL-регресс [TD-044](../../100-known-tech-debt.md): сессия, открывшаяся БЕЗ поколения, обязана взвести сверку** ([ADR-067 §3.3.1a](../../adr/ADR-067-agent-run-background-consumer.md)). Сценарий: `current_epoch` при открытии даёт `None` (ключа нет **или** Redis не ответил — оба случая, они склеены намеренно) → клиент подключается → **позже** поколение появляется/меняется, `seq` идёт с `1`. Ожидание: клиент **получает события нового поколения**. ⚠️ **Тест обязан падать на реализации `generation = epoch or ""` со сверками под `if current_generation`:** там сессия живёт без §3.3.1 до конца, все события отбрасываются дедупом, правила закрытия не срабатывают (lease жив) — **навсегда открытый молчащий стрим без единого признака в логах**. **Формулировать через инвариант, а не через строки кода:** «событие не отдаётся клиенту при невзведённой сверке поколения». Три подслучая: (а) ключа нет, но ring непуст → поколение берётся из последнего отданного элемента; (б) ключа нет, ring пуст, **курсор пуст** → **усыновление** первого увиденного поколения **из события**, `run.truncated` **не отдаётся** (парный негатив: маркер в этом сценарии — шум, сообщать о неполноте префикса тому, у кого префикса нет, нечего); (в) то же для **тихого** прогона — усыновление из **периодической сверки**, без единого события; (г) ⚠️ **ключа нет, но клиент пришёл с непустым курсором** (`Last-Event-ID: <старый epoch>-500`) → `run.truncated` **обязателен**: без него клиент молча склеит два поколения. **Тест обязан падать на реализации, где усыновление всегда молчаливо** — поведение не имеет права зависеть от того, ответил ли Redis, при читаемом ключе тот же клиент получил бы маркер по §3.2 шаг 2.
- **CRITICAL-регресс [TD-045](../../100-known-tech-debt.md): сброс `seq` БЕЗ смены `epoch`** ([ADR-067 §3.3.1b](../../adr/ADR-067-agent-run-background-consumer.md)). Сценарий: клиент подключён и получил события до `seq=500` → прогон молчит дольше `AGENT_RUN_EVENT_BUFFER_TTL_SECONDS` (в тесте — короткий TTL), ключи ring'а истекают, **lease жив** (`RENEWED`) → приходит новое событие со **старым** `epoch` и `seq=1`. Ожидание: клиент **получает** это событие, предварённое `run.truncated`. ⚠️ **Тест обязан падать на сегодняшней реализации:** поколения совпадают ⇒ §3.3.1 молчит, дедуп отбрасывает `1 <= 500`, периодическая сверка получает `None` ⇒ **молчащий стрим до конца прогона**. Проверять **обе** меры **раздельно, каждую своим наблюдаемым признаком** (по одной мутации за прогон — правило нейтрализации):
  - **(а) consumer, `ensure_epoch` на КАЖДОМ тике продления.** ⛔ **Ассерт «клиент получил событие с маркером» для этой меры НЕГОДЕН — он маскируется мерой (б):** при снятой профилактике событие всё равно доходит и всё равно с маркером, тест остаётся зелёным и о мере (а) не доказывает ничего. **Признак меры (а) не зависит от broker'а вовсе и снимается из Redis и из потока consumer'а:** у молчащего прогона с живым lease после истечения TTL ключ `agent:run:{runId}:epoch` **(i)** существует снова **не позже одного тика продления**, **(ii)** его значение **отличается** от прежнего, **(iii)** ближайшее опубликованное событие несёт в поле `epoch` **именно новое** значение. Мутация: вернуть `ensure_epoch` только на `REACQUIRED` ⇒ краснеет (i)–(iii). Отдельный ассерт следствия: **`id: <epoch>-<seq>` остаётся уникальным** — без меры (а) `seq` идёт по второму кругу под тем же `epoch`;
  - **(б) broker, `arrived` против `delivered`.** Мутация: сравнивать с `delivered` ⇒ ложный `run.truncated` на штатном перекрытии «ring + live». ⚠️ **ПРЕДУСЛОВИЕ: эта мутация инертна, пока не исправлен [TD-047](../../100-known-tech-debt.md)** — перекрытия «ring + live» сегодня **не существует** (код делает `LRANGE` до `SUBSCRIBE`, подписка вдобавок ленивая), поэтому парный негатив ниже зелёный при **обеих** реализациях дискриминатора. Либо порядок §3.2 шаг 1 приходит тем же изменением, либо в тесте стоит `xfail`-пометка с cross-ref на TD-047 и мутация не считается снятой.

Оба уровня обязательны, и ни один не заменяет другой; сегодня такое сообщение отбрасывается буквально молча (`if event is not None:` без `else`), тогда как путь ring'а warning пишет. ⚠️ Парный тест безопасности: в логе **нет** user content. ⛔ **Причина УСТАНОВЛЕНА ([Q-067-21](../../99-open-questions.md) закрыт), и она вне всех трёх заявленных кандидатов: `logger.disabled = True`** — `Logger.handle()` короткозамыкает до любого хендлера, включая корневой. Тест обязан падать, если ретраи появятся в `get_event_bus_redis` без сверки `epoch` при восстановлении подписки.

Воспроизведено qa на реальном Redis: `?afterSeq=500`, ключ поколения **читаем**, максимальный `seq` в ring `3` ⇒ реплей отдаёт **ноль без маркера**, `delivered = 0`, live-события отброшены, стрим **открыт и пуст**. ⚠️ **Ни рестарта Redis, ни истечения TTL, ни смены поколения не требуется** — один HTTP-запрос штатным параметром. Ожидание после фикса: клиент получает `run.truncated` **сразу при открытии** (маркер порождается в `stream()`, а не в `_replay_blocks`), полный реплей ring'а `1..3` и **все** live-события. **Три независимых ассерта, каждый со своей мутацией:** **(1)** baseline дедупа **не** инициализируется курсором (мутация: `delivered = cursor.seq` ⇒ стрим пуст ⇒ красный); **(2)** числовой гард `cursor.seq > current_seq` обнуляет курсор (мутация: убрать гард ⇒ реплей `1..3` съеден ⇒ красный); **(3)** курсор **без `epoch`** всегда сопровождается маркером (мутация: молчаливое принятие ⇒ красный). ⚠️ Сегодня **все три красные**: гарда в коде нет, `transport.current_seq()` не вызывается из `src/` ни разу, а условие `cursor.epoch is not None and …` для `?afterSeq=` ложно при любом поколении.
- **Ось C — оповещение, отдельная группа ассертов** ([ADR-067 §3.2.1](../../adr/ADR-067-agent-run-background-consumer.md); критерий приёмки — `A ∧ B ∧ C`, и **два из четырёх** известных входов были именно C при корректном сравнении): **(1)** маркер отдаётся при пустом наборе реплея — рождается в `stream()`, а не в `_replay_blocks`; **(2)** маркер отдаётся **из периодической** ветки сверки поколения, не только из событийной; **(3)** маркер отвергнутого курсора несёт **`seq = 0`** и **не двигает** baseline (⚠️ негатив: с сырым `seq` курсора клиент запомнил бы `id: <epoch>-500` и переподключался бы с уже отвергнутым курсором — отказ стал бы самоподдерживающимся); **(4)** ⛔ **`?afterSeq=0` — маркера НЕТ по основанию C5**, то есть **только при ПОЛНОМ ring'е** (нулевой курсор пуст и тождествен отсутствию; правило «всегда маркер» относится к `afterSeq > 0`). ⚠️ **Негатив ставится строго на полном ring'е:** при `?afterSeq=0` и **обрезанном** ring'е маркер **обязателен** по C3 (первый отданный `seq` > 1). Безусловный ассерт «при `afterSeq=0` маркера нет» упадёт на **корректной** реализации.

Парный негатив: первое подключение к **полному** ring'у (первый `seq` = 1) — маркера нет.
- ⛔ **Эффект на `delivered` у C1a и C1b ПРОТИВОПОЛОЖНЫЙ — два отдельных ассерта, унификация запрещена** ([ADR-067 §3.2.1](../../adr/ADR-067-agent-run-background-consumer.md)): **C1a** (перезапуск счётчика, `event.seq <= arrived`) ⇒ маркер + **`delivered = 0`** + отдать; **C1b** (дырка ниже метки, `event.seq < replay_min_seq` при монотонном приходе) ⇒ маркер + отдать, **`delivered` НЕ меняется**. **Две обязательные мутации:** **(1)** «всегда обнулять» ⇒ после дырки (`35` при метке `40`) событие `41` даёт лишний маркер по C2, а дубли перекрытия начинают переотдаваться; **(2)** «никогда не обнулять» ⇒ при сбросе событие `1` отдано с маркером, `delivered` остался `500`, событие `2` гасится дедупом, `arrived` уже монотонен ⇒ **события `2..500` теряются молча — [TD-045](../../100-known-tech-debt.md) целиком возвращается**.

Обе трактовки обязаны сосуществовать — «унификация» ломает одну из них.

- **`process_event` возвращает синтетический `run.paused`**, а не отдаёт его сама: проверить, что **оба** контура доводят его до потребителя — relay через `yield` клиенту, consumer публикацией в ring — и что оба останавливают обработку прогона по этому же объекту.

**Живость выводится из прогресса, а не из расписания ([ADR-067 §6.1](../../adr/ADR-067-agent-run-background-consumer.md)):**
- **Молчащий, но живой upstream:** нет доменных событий 10–15 минут (длинный tool-call) → consumer **НЕ** самозавершается, heartbeat идёт (`state = awaiting_upstream`), lease держится, reaper прогон не трогает, клиентский стрим **не закрывается**. ⚠️ Регресс отозванного idle-таймаута — тест обязан падать на реализации с порогом по молчанию доменных событий.
- **Зависание НАШЕЙ обработки (CRITICAL-регресс):** рабочая задача входит в `processing` и не выходит (мок блокирующей записи в БД) дольше `AGENT_RUN_PROCESSING_STALL_SECONDS` при **живом сокете и живом пире** → супервизор **прекращает heartbeat, снимает lease и отменяет рабочую задачу**; прогон становится кандидатом reaper'а. ⚠️ Тест обязан падать на реализации, где heartbeat/lease — независимые от прогресса периодические задачи.
- **Beacon выставляется НА ПЕРЕХОДЕ, а не после итерации (регресс MAJOR):** сценарий «итерация завершилась → пришло событие → обработчик завис». Если `processing` выставляется **перед** входом в обработку — зависание детектируется за `STALL`; если после итерации — beacon остался бы в `awaiting_upstream`, что означает «живы» безусловно, и зависание **не было бы замечено никогда**. Тест обязан ловить именно эту разницу.
- **Прогресс, а не оборот цикла:** цикл быстро крутится (состояния меняются), но `bytes_read` и `last_published_seq` **не растут** дольше `STALL` → зависание.
- **`bytes_read` считается по приходу СЫРОГО ЧАНКА, а не по завершённым SSE-блокам** ([ADR-067 §6.4.2](../../adr/ADR-067-agent-run-background-consumer.md)): подписка, принимающая **крупное первое событие** и ещё не дособравшая блок, обязана иметь `bytes_read > 0` и **не** попадать под guard. ⚠️ Тест обязан падать на реализации со счётом по блокам — там guard убил бы работающий прогон. Состояние `connecting` лимитом **не свободно** (в отличие от `awaiting_upstream`).
- **`MAX_DURATION` применяется супервизором через отмену** рабочей задачи, а не внутренним таймером: сценарий «рабочая задача зависла + истёк потолок» обязан завершиться, а не зависнуть.
- **Длинный tool-call НЕ признаётся зависанием (регресс чтения §6.1):** прогон в `awaiting_upstream` 20+ минут без единого события → heartbeat **идёт**, lease продлевается, свип прогон **не трогает**. ⚠️ Тест обязан падать на реализации «heartbeat только если выросли счётчики» — там свип финализировал бы **живой** прогон.
- **Крутящийся цикл ловится:** `>= 4` перехода `processing` ↔ `awaiting_upstream` за окно `STALL` **без** роста `bytes_read`/`last_published_seq` → зависание. Парный негатив: **2** перехода (одна неудачная итерация) зависанием **не** считаются.
- **Продление lease трёхзначно (§4):** ключ наш → `RENEWED`; **ключа нет** (эмуляция перезапуска Redis) → `REACQUIRED`, consumer **продолжает** и **переустанавливает `epoch`**, а рабочая задача публикует уже под новым поколением; ключ чужой → `LOST` → §6.4. ⚠️ Два теста обязаны падать на прямолинейной реализации: (а) при стёртом ключе **все** consumer'ы не должны самозавершаться; (б) после `REACQUIRED` подписчик обязан получить события (при старом `epoch` broker отбросил бы их и стрим стал бы молчащим).
- **Финальный флаш §6.4 ограничен `5 с`:** мок «зависшая запись в БД» → снятие lease и audit всё равно происходят. ⚠️ Регресс: неограниченный флаш завис бы там же и не дошёл до снятия lease.
- **Строка `agent_runs` создаётся и КОММИТИТСЯ до ожидания handshake** ([ADR-067 §6.1.2](../../adr/ADR-067-agent-run-background-consumer.md)): при падении процесса **во время** ожидания строка уже есть, и прогон достижим для orphan-свипа. ⚠️ Тест обязан падать на реализации, где handshake ждут **до** `create_running`: прогон существует на инстансе, но не в БД — его не добьёт никто.
- **Ожидание handshake идёт без открытой транзакции:** в момент ожидания коннект возвращён в пул (проверять по счётчику занятых коннектов / `pg_stat_activity`). ⚠️ Регресс на класс [TD-040](../../100-known-tech-debt.md).
- **Таймаут handshake не фатален:** мок «подписка не отвечает заголовками» → `POST /v1/agent/run` отдаёт **`202`** в пределах `AGENT_RUN_HANDSHAKE_TIMEOUT_SECONDS`, пишется audit `agent_run_consumer_handshake_timeout`, consumer **не отменён**. Парный негатив: ожидание **не** длится `AGENT_RUN_FIRST_BYTE_STALL_SECONDS`.
- **Milestone — после `2xx`, до первого события:** подписка установлена, но событий нет минуты → `202` отдан **сразу** после установки. ⚠️ Тест обязан падать на реализации, ждущей первого события: там латентность `POST` выросла бы до появления контента ([Q-067-14](../../99-open-questions.md)).
- **Handshake сигнализирует оба исхода:** при отказе consumer'а на **любом** пути завершения ожидающий обработчик разблокируется немедленно, а не по таймауту (backstop).
- **Сессия БД не удерживается через `await` на upstream** ([ADR-067 §6.1.1](../../adr/ADR-067-agent-run-background-consumer.md)): в момент ожидания события у consumer'а **нет** открытой сессии/транзакции — проверять по счётчику занятых коннектов пула либо по `pg_stat_activity`. ⚠️ Прямой регресс на класс [TD-040](../../100-known-tech-debt.md).
- **`consumers=None` = контур выключен:** приложение **без `lifespan`** (тестовый клиент) и `AGENT_RUN_CONSUMER_ENABLED=false` дают **одинаковый** путь запуска — ровно как до [ADR-067](../../adr/ADR-067-agent-run-background-consumer.md), без ветвлений в бизнес-логике. ⚠️ Проверять обоими способами: отсутствие реестра не должно требовать отдельной ветки в `service.run()`.
- **Audit из consumer'а идёт через `ServiceFactory`** (`service.record_consumer_event`), а не через `AuditService`, связанный с сессией: в момент записи audit сессия берётся и возвращается, а не удерживается на весь прогон. ⚠️ Регресс на правило «сессия по операции» ([ADR-067 §6.1.1](../../adr/ADR-067-agent-run-background-consumer.md)).
- **Реестр задач в `lifespan`:** consumer-задачи **достижимы** из реестра (не fire-and-forget); при остановке воркера все отменяются, §6.4 отрабатывает в пределах `AGENT_RUN_SHUTDOWN_DRAIN_SECONDS`, **порядок соблюдён** — отмена consumer'ов **до** закрытия пула БД и Redis. ⚠️ Проверять **по фактическим позициям вызовов в `lifespan`**, а не по намерению: при обратном порядке §6.4 не сможет ни доflushить снапшот, ни снять lease, и штатная остановка выродится в аварийную.

- **Смерть супервизора отменяет рабочую задачу (MAJOR-регресс, `TaskGroup`):** супервизор снят принудительно → **рабочая задача тоже отменена**; прогон честно осиротел. ⚠️ **Тест обязан падать на реализации, где рабочая задача продолжает работу:** там reaper через `ORPHAN_TIMEOUT` пометил бы **работающий** прогон `failed` и списал по неполному кумулятиву с `idempotency_key=runId`, после чего штатная финализация с **тем же ключом** была бы отброшена как дубль (недобор окончателен и молчалив), а `_mark_terminal('completed')` стал бы no-op по условному переходу — прогон **навсегда `failed`**. Парная проверка: отмена рабочей задачи отменяет супервизор.
- **Мёртвый пир:** закрытие сокета → ошибка чтения → §6.4 (флаш, снятие lease и heartbeat, audit `agent_run_consumer_disconnected`), **без** переподключения и **без** терминального статуса.
- **Ретрая подписки нет ни при какой причине отказа** ([ADR-067 §6.4.1](../../adr/ADR-067-agent-run-background-consumer.md), H10 опровергнута замером): и обрыв установленной подписки, и отказ на connect-фазе → сразу §6.4. ⚠️ Тест обязан падать на реализации, где есть connect-retry подписки.
- **Guard на инертную подписку** ([ADR-067 §6.4.2](../../adr/ADR-067-agent-run-background-consumer.md)): подписка установлена (заголовки получены), но **ни одного байта** дольше `AGENT_RUN_FIRST_BYTE_STALL_SECONDS` → супервизор снимает lease/heartbeat и отменяет рабочую задачу. **Парный негатив (критичный):** поток, отдавший хотя бы один байт и затем молчащий дольше порога, **НЕ** трогается — guard действует только при `bytes_read == 0`, иначе это был бы воскресший idle-таймаут. ⚠️ Парный негатив: ошибка **после получения заголовков** (`ReadError`/`ReadTimeout`/`RemoteProtocolError`) и любой non-2xx → **ретрая нет**, сразу §6.4. Тест обязан ловить обе границы — запрет, распространённый на connect-фазу, стоил бы навсегда бесплатного прогона.
- **Исчерпание connect-ретраев:** `POST /v1/agent/run` всё равно отдаёт `202`, audit `agent_run_consumer_failed`, прогон подхватывает reaper.
- **Шаг 2 §6.4 выполняется даже при неуспехе шага 1:** финальный флаш снапшота упал/завис → lease и heartbeat всё равно сняты.

**Heartbeat не протекает в клиентский контракт:**
- **Heartbeat ВСЕГДА идёт отдельным `UPDATE … SET consumer_heartbeat_at = now()`** и **НЕ двигает** ни `agent_run_snapshots.updated_at`, ни `agent_runs.updated_at` — проверять **оба** случая: и при длительном молчании прогона, и когда события идут (исключений для второго нет). ⚠️ Тест обязан падать на реализации, где heartbeat выполняется обычным апсертом снапшота (тот пишет `updated_at` безусловно → утечка в `/state.updatedAt`, обесценивающая миграцию `0020`).
- `GET …/state` при отсутствующей строке снапшота отдаёт `updatedAt`, **не зависящий** от heartbeat'а. ⚠️ Тест обязан падать на реализации, где heartbeat пишется в `agent_runs.updated_at`.
- **Строка снапшота создаётся при старте consumer'а** (ради heartbeat'а), поэтому ветка «снапшота нет» при живом consumer'е недостижима — проверяется отдельно для `AGENT_RUN_CONSUMER_ENABLED=false` и для прогона, у которого consumer не встал.

**Миграция `0020` (real DB, testcontainers):** `upgrade`+`downgrade`; `alembic heads` == 1 (цепочка `0019`→`0020`); колонка `consumer_heartbeat_at` и частичный индекс **`ix_agent_runs_active`** на **`agent_runs`** (`(created_at) WHERE status IN ('running','resumed')`) создаются/удаляются. ⚠️ Индекса по `consumer_heartbeat_at` быть **не должно** — состав индексов `agent_run_snapshots` остаётся **два** ([ADR-066 §7](../../adr/ADR-066-agent-run-state-snapshot.md)).

**Kill-switch и гибернация:**
- При `AGENT_RUN_CONSUMER_ENABLED=false` поведение совпадает с легаси ([TD-038](../../100-known-tech-debt.md)).
- Consumer обновляет `hermes_instances.last_active_at`; `stop_idle` не гасит инстанс с активным прогоном.

**E2E (ручной, прод-подобный) — ОДИН критерий приёмки:**

1. **Корректность учёта:** запустить прогон → **не открывать** `/events` вовсе → дождаться завершения → `GET …/state` показывает терминальный статус и непустой `resultText`, `GET /v1/wallet` показывает списание, `trialRemaining` уменьшился.

**Приёмка Phase 9 — по одному критерию (учёт):** прогон без подписчика получает терминальный статус, списание и непустой `resultText`.

**Что осталось от прежних замеров как полезное:**
- рецепт воспроизведения (обрыв подписки до первого байта, контрольный пользователь, повтор через 120 с) — годен для **tripwire** [Q-067-17](../../99-open-questions.md);
- различение причин **по коду ответа, без SSH**: `502 upstream_timeout` ⇒ инстанс нем; `202` ⇒ инстанс жив (round-trip состоялся).
- ⚠️ **Третье звено — `HTTP=000`/зависание — это НАБЛЮДЕНИЕ, а не диагноз.** Прежняя формулировка «⇒ невыявленный лок-путь у нас» **снята**: она атрибутирует компоненту симптом **без кода ошибки**, что запрещает вывод 2 в [06-testing-strategy.md §Методические выводы](../../06-testing-strategy.md) — и уводит разбирающего от второго документированного кандидата. **Кандидаты (минимум два, различающего признака пока нет):**
  1. **невыявленный лок-путь у нас** — класс [TD-040](../../100-known-tech-debt.md) (закрыт: удержание row-lock через сетевой вызов; но класс «наш await без эффективного дедлайна» не исчерпан);
  2. **зависший docker-демон** — [TD-041](../../100-known-tech-debt.md) (**открыт**): вызовы docker-py идут в `asyncio.to_thread`, **не отменяемы и вне** `HERMES_LAUNCH_BUDGET_SECONDS`, поэтому при зависании демона запрос снова становится бесконечным — и, в отличие от кандидата 1 после фикса, **не наблюдается** как `502 upstream_timeout`.

  **Различающий признак — ФАЗА, на которой висит запрос:** провижининг/готовность контейнера (`readiness`, docker-лега ⇒ [TD-041](../../100-known-tech-debt.md)) против проксирования к уже работающему инстансу (`launch`/`connect`, наша лега ⇒ класс [TD-040](../../100-known-tech-debt.md)). Фаза уже размечена в счётчике tripwire `agent_run_launch_upstream_timeout_total{phase}` ([Q-067-17](../../99-open-questions.md), `phase` ∈ `{connect, readiness, launch, hydrate, budget}`) — ⚠️ **но он считает истёкшие таймауты, а при `HTTP=000` таймаут не срабатывает вовсе**, поэтому на зависании счётчик молчит. Фазу в этом случае даёт **последний пройденный шаг launch-пути** в логах/audit. ✅ **Поправка (проверено по коду 2026-07-31):** лог-событие `agent_run_launch_upstream_timeout` **несёт `phase`** наряду с `userId`/`runId`/длительностью — прежнее утверждение «поля `phase` в нём нет» было выведено из спецификации п. 6 фаз, а не из кода, и **неверно**; отдельной задачи на разметку не требуется.

  ⚠️ **Покрытие tripwire НЕ полное — две границы с известной причиной** ([ADR-067 §5.1](../../adr/ADR-067-agent-run-background-consumer.md), [Q-067-17](../../99-open-questions.md)): **(1)** `ConnectError` (refused/reset) в счётчик не попадает намеренно — ищется **немота**, а не отказ; смешанный режим «отказ на первых попытках, приём на последней» невидим; **(2)** passthrough `POST …/stop` и `…/approval` не инструментирован — `502 upstream_timeout` там возникает, но счётчика и лога нет, а `/stop` — самый показательный запрос при зависшем прогоне. Поэтому при разборе зависания **отсутствие роста счётчика ничего не доказывает**: проверять и коды ответов `/stop`. **До установления фазы симптом фиксируется как наблюдение со списком кандидатов; строить на одном из них механизм запрещено.**

⚠️ **Tripwire (наблюдение, не тест):** кластеризация `502 upstream_timeout` **по одному пользователю** после прогонов без дренажа возвращает предпосылку и воскрешает §5.1 — тогда возвращаются и критерий 2, и колонка `first_byte_at`.

**E2E клиентского контракта ([ADR-067 §3.4](../../adr/ADR-067-agent-run-background-consumer.md)):** два последовательных подключения к `/events` одного прогона → второе получает **полный реплей с начала**. Зафиксировать явно: клиент, склеивающий `message.delta` поверх соединений, удвоит текст — согласовать с iOS до выкатки.

## Безопасность
- `API_SERVER_KEY` не появляется в логах/ответах клиенту (redaction).
- `result_text`/`pending_approval` (user-content, [ADR-066](../../adr/ADR-066-agent-run-state-snapshot.md)) не попадают в логи и audit-события; `/state` чужого прогона недоступен (404).
- Bearer к инстансу никогда не пробрасывается клиенту; клиент видит только ретранслированные доменные события.
