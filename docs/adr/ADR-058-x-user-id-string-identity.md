# ADR-058 — `X-User-Id` принимает произвольную непустую строку (детерминированный маппинг в UUID)

- Статус: Accepted
- Дата: 2026-07-06
- Расширяет: [ADR-044 §1/§3](ADR-044-client-api-key-auth.md) (клиентский контур `X-API-Key` + `X-User-Id`, модель доверия к идентичности) — тело ADR-044 не переписывается (immutability); канал резолвинга субъекта уточняется здесь.
- Связан с: [ADR-007](ADR-007-lazy-user-provisioning.md) (lazy provisioning — без изменений), [05-security.md](../05-security.md), [08-api-documentation.md](../08-api-documentation.md), [API-REFERENCE.md](../API-REFERENCE.md)

## Context

По [ADR-044](ADR-044-client-api-key-auth.md) идентичность субъекта клиентского контура берётся из заголовка `X-User-Id`, который резолвится строго как UUID: `get_current_user` (`src/app/deps.py`, стр. 111–116) делает `uuid.UUID(x_user_id.strip())` и при `ValueError` отдаёт `401`. Любой `X-User-Id`, не являющийся канонической UUID-строкой (например внешний стабильный идентификатор пользователя из control plane клиента — email, аккаунт-id, tenant-scoped id), отклоняется.

Интеграционному клиенту (control plane, владеющий идентичностью пользователей) неудобно хранить и передавать именно UUID: у него есть **свой** стабильный идентификатор пользователя произвольного формата. При этом:

- `users.id` — **UUID PK**, на который завязано ~15 FK (`subscriptions`, `wallets`, `byok_keys`, `ledger_transactions`, `chat_sessions`/`chat_steps`/`tool_calls`, `audit_logs`, Hermes-инстансы и др.). Менять тип PK на строку — недопустимо (миграция ~15 таблиц, потеря инвариантов).
- Уже существуют пользователи и admin-гранты, заведённые под каноническими UUID (`X-User-Id = <uuid>`). Обратная совместимость обязательна: тот же UUID-заголовок обязан резолвиться в тот же `users.id`.

Нужен способ принять **любой** стабильный строковый идентификатор, не трогая тип PK и не ломая существующие UUID-субъекты.

## Decision

### 1. Резолвинг `X-User-Id` в `get_current_user` (`src/app/deps.py`)

Заголовок `X-User-Id` принимает **любую непустую (после `strip()`) строку**. Порядок резолвинга субъекта в `users.id` (UUID) — детерминированный:

1. **Пустой / whitespace-only заголовок → `401`** (нет субъекта; без изменений относительно ADR-044). Проверка выполняется по **уже обрезанному** значению: `raw = x_user_id.strip()`; если `not raw` → `401`.
2. **`raw` парсится как канонический UUID → использовать КАК ЕСТЬ** (`user_id = uuid.UUID(raw)`). Обеспечивает обратную совместимость: существующие пользователи и admin-гранты, заведённые под UUID, резолвятся в тот же `users.id`.
3. **Иначе (не UUID) → `user_id = uuid.uuid5(HERMES_USER_NAMESPACE, raw)`** — стабильный (детерминированный) UUIDv5 из строки. Одна и та же строка всегда даёт один и тот же `users.id` → та же подписка, кошелёк, BYOK, Hermes-агент.

Никакого `401` по «формату» `X-User-Id` больше нет: единственная причина `401` от резолвинга субъекта — пустой/whitespace заголовок (плюс, раньше по цепочке, невалидный/отсутствующий `X-API-Key`).

### 2. Namespace-константа `HERMES_USER_NAMESPACE` — ФИКСИРОВАНА и НЕИЗМЕНЯЕМА

- Значение: **`638724f1-2181-4d61-96de-5b8eedf7ef7a`** (UUIDv4, сгенерирован однократно при принятии этого ADR).
- Объявляется как **код-константа** (module-level), НЕ как env-переменная и НЕ как настройка `Settings`. Причина: env/настройку можно случайно переопределить или потерять между инстансами → сместятся ВСЕ производные `users.id` (uuid5 от той же строки даст другой UUID) → пользователи «потеряют» свои подписки/кредиты/агентов. Хардкод + явный комментарий об immutability исключает этот класс ошибок.
- **Инвариант (must-not-change-after-launch):** после первого продакшн-запуска значение `HERMES_USER_NAMESPACE` менять НЕЛЬЗЯ. Смена namespace эквивалентна миграции идентичностей всех uuid5-пользователей и здесь не предусмотрена. Изменение возможно только новым ADR с явным планом ре-маппинга.
- Значение одинаково на всех инстансах (в отличие от per-instance `CLIENT_API_KEY`): детерминизм `строка → users.id` должен быть глобальным.

### 3. Инварианты, которые НЕ меняются

- `users.id` остаётся **UUID PK**; ~15 FK не трогаются; **миграций НЕТ**.
- Lazy provisioning ([ADR-007](ADR-007-lazy-user-provisioning.md)) — без изменений: `provision_user(session, user.user_id)` вызывается после резолвинга субъекта, `INSERT ... ON CONFLICT (id) DO NOTHING`. Меняется только способ вычисления `user_id`, не семантика провижининга.
- Модель доверия ([ADR-044 §3](ADR-044-client-api-key-auth.md)) — без изменений: идентичность доверяется, т.к. `X-API-Key` доверенный. Знание ключа = право действовать за любой `X-User-Id` (теперь — за любую строку).
- `require_owner` остаётся no-op ([ADR-044 §3](ADR-044-client-api-key-auth.md)).
- Trimming: ведущие/замыкающие пробелы обрезаются (`strip()`) до всех проверок — и для UUID-ветки (padded UUID работает, как раньше), и для uuid5-ветки (namespace-хэш берётся от обрезанной строки), чтобы `" foo "` и `"foo"` резолвились в один субъект.

### 4. OpenAPI security-схема `userId`

Описание схемы `userId` (`src/app/api_gateway/openapi_security.py`) и упоминания «`X-User-Id` = UUID» в docs переформулируются на «**стабильный строковый идентификатор** субъекта» (каноническая UUID-строка используется как есть; иная строка детерминированно маппится в UUID). Тип схемы (`apiKey`, header, `X-User-Id`) и AND-контракт с `clientApiKey` — без изменений.

## Consequences

**Положительные:**
- Клиент передаёт свой естественный стабильный идентификатор пользователя без конвертации в UUID на своей стороне.
- Обратная совместимость полная: существующие UUID-субъекты и admin-гранты не смещаются.
- Ноль миграций, PK и FK-граф не тронуты.
- Детерминизм: `строка → users.id` стабилен и воспроизводим (uuid5), одинаков на всех инстансах.

**Отрицательные / ограничения:**
- `HERMES_USER_NAMESPACE` — новый must-not-change инвариант. Его смена = скрытая массовая «потеря» uuid5-пользователей. Митигация: хардкод-константа + комментарий immutability + этот ADR.
- Теоретическая коллизия двух разных строк в один uuid5 — криптографически пренебрежима (SHA-1-based UUIDv5, 122 бита).
- Крайний edge-case: строка, которая СЛУЧАЙНО является канонической UUID-формой, трактуется как UUID (ветка 2), а не хэшируется. Это осознанно (обратная совместимость важнее). Клиент, использующий произвольные строки, не должен подавать строки в UUID-формате, если не имеет в виду именно тот UUID-субъект.

## Alternatives

1. **Сменить тип `users.id` на строковый.** Отвергнуто: миграция ~15 FK-таблиц, потеря UUID-инвариантов, высокий риск. uuid5-маппинг даёт тот же эффект без изменения схемы.
2. **Хранить внешнюю строку в отдельной колонке `users.external_id` с lookup.** Отвергнуто на старте: требует миграцию + индекс + ветку lookup/insert в hot-path; uuid5 детерминирован и не требует хранения маппинга (строку всегда можно пересчитать в тот же id).
3. **`HERMES_USER_NAMESPACE` из env/Settings.** Отвергнуто: риск рассинхронизации между инстансами / случайной смены → катастрофический сдвиг всех производных id. Хардкод строго безопаснее.
4. **Оставить строгий UUID (статус-кво).** Отвергнуто решением пользователя: клиенту неудобно навязывать UUID-формат идентификатора.
